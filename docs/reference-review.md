## 2. 真正值得补入的内容

### 2.1 执行轨迹没有自动生成反事实标签

原稿第六节明确指出：只观察到执行方案 A 后的结果，不能同时得到 B、C 的结果标签。这应成为方案排序、胜率预测和模仿数据的共同约束。

采纳方式：在 [方法论](methodology.md) 与 [实验模板](../templates/experiment.md) 中区分四种数据来源。

1. **观测结果**：实际执行的方案及后续结果。可用于对应条件下的结果预测；“后来获胜”本身不能证明当时的动作导致了获胜。
2. **受控干预结果**：经过验证的状态恢复或脚本前缀重建后，运行不同候选；同时记录对手与己方后续控制策略、观察历史、采样误差和状态匹配程度。
3. **参考意见**：人类或另一个控制器给出的偏好、理由与不确定性。它是参考判断，不能伪装成真实引擎已经执行过的结果。
4. **模型预测/伪标签**：基于明确假设和适用范围估计未执行方案，可作为探索或训练辅助；须独立验证并保留来源，不能当作实际观测或引擎反事实真值。

缺少干预数据时，可以先训练已执行方案的结果预测器；但必须检查动作覆盖范围与数据来源变化，不能凭离线预测精度声称它能可靠挑选未覆盖方案。若以后采用离线因果估计或离线 RL，需要额外说明识别假设与分布覆盖，本阶段不默认这些条件成立。

### 2.2 “不发新命令”必须作为有语义的控制器审计

原稿第三节提醒 no-command 不等于无行为，值得独立落入 [环境审计](environment-audit.md) 和 [评测](evaluation.md)。在具体引擎行为测定前，这是一项需要检验的风险，不能直接断言所有单位都会怎样自动行动。

机制实验至少区分：保持既有指令后不再发令、初始化后从未发令、显式停止，以及固定时序脚本。每个基线记录初始目标、命令队列、单位状态和后续实际移动/攻击。这样才能识别学习模块相对于既有命令与引擎自带行为的增量。

不能把 no-command 基线写成“静止敌人”，也不能把它取得的收益全部归因于学习。显式停止同样有自己的 API 语义，不是天然纯净的对照。

### 2.3 外部控制器与同步游戏循环内代码分开设计

原稿第二节的部署区分已有官方资料依据：[Game API 文档的确定性说明](https://www.npmjs.com/package/%40chronodivide/game-api?activeTab=readme) 区分外部 sandbox bot 与集成进游戏循环的代码，后者需要满足确定性要求，避免同步和回放问题。这是**文档核实**，不是本仓库已经验证某种模型部署方式可行。

采纳到 [环境审计](environment-audit.md)：在实现推理前明确命令在哪里生成、哪些代码参与同步模拟、结果在哪个 tick 生效、是否有异步接口与时限、如何记录命令以及如何重放。外部策略可能包含随机性，不意味着接口允许任意异步延迟；仍须控制实验随机源并测定时序。同步循环内推理则要额外审计数值运算、随机源、依赖库与跨运行一致性。

这项区分用于提前暴露约束，不要求现在同时实现两种后端，也不根据“小模型”三个字推断部署成本。

### 2.4 建筑放置需要检验持续影响

原稿第四节把“当前位置允许建造”与“建造后基地能继续工作”分开，这是对执行可靠性的重要补充。

采纳到 [方法论](methodology.md) 的建筑规划接口和 [环境审计](environment-audit.md) 的机制案例：检查建造后的生产出口、矿车往返、部队集结路线及后续扩建空间；日志关联放置决策与随后出现的堵路、采矿中断或生产停滞。必要时从真实堵路故障构造回归案例，并延长观察到后续生产和移动发生。

**限定**：不能把“保证所有未来通路”设为当前必须求解的无限规划问题。已验证的不可放置与关键通道完全阻断可作为约束；扩建空间、未来拥堵风险等首先是可比较的规划偏好。规则应按单位通行机制、地形和任务验证，避免排除合法的防守封堵打法。

### 2.5 人工审查需要筛选，也需要抽查

原稿第九节建议优先把新故障、控制器分歧、模型不确定性高，以及局部指标改善而整局退步的案例交给人类。采纳到 [路线图](roadmap.md) 与 [实验模板](../templates/experiment.md)，每次提交最少必要的回放片段、状态记录、候选解释和可被否定的判断。

额外补充：保留少量随机抽查与按地图、对手、任务分层的样本。只看模型高不确定性案例会漏掉自信的错误；只看失败会漏掉靠对手失误掩盖的缺陷。人工审查样本用于发现问题，不能直接当成总体故障率或胜率的无偏样本。

重复出现且语义已经清楚的结论进入机器检查；新颖、尚不确定的因果判断仍作为假设。不要把“人类看过”写成场景永久可信的认证。

### 2.6 四层评测与三类证据可以同时保留

原稿的四层描述的是**实验组织方式**；已接受的三类证据描述的是**允许支持的结论**。两者无需竞争命名，也不需要增加一套独立晋升流程。

| 四层实验 | 主要证据类别 | 可支持与不可支持的结论 |
| --- | --- | --- |
| 机制测试 | 机制/软件正确性 | 可核查特定版本中的行为；不代表实战代表性 |
| 真实局面的局部测试 | 局部决策能力 | 可比较所保留上下文中的候选；不代表整局增益 |
| 受约束的场景扩展 | 局部能力的稳健性证据 | 可检查合法扰动内的敏感性和泛化；扩展范围不自动等于目标对局分布 |
| 完整对局验收 | 整局竞争力 | 可在冻结的地图、规则和对手分布下估计效果；不外推为所有 RA2 条件下的实力 |

此表进入 [评测](evaluation.md)。另一个独立维度是“来源已核实、运行已测量、假设、建议默认值”的证据状态；不要把“局部实验”误写成“已经执行过的实验”。

### 2.7 分叉应保存策略历史，并让对手响应

原稿第五节对画面、引擎状态和 AI 内部状态的区分应纳入 [环境审计](environment-audit.md)：朝向、攻击阶段、队列、弹丸等是待核查的状态项目；任务归属、记忆与循环网络隐藏状态也是控制器上下文。复制单位坐标和血量并不能默认恢复这些条件。

改变己方策略之后，继续机械执行原回放的对手命令，只能构成对固定动作序列的测试。反应式对手可使比较更接近闭环，但仍要记录其版本与局限；并不等于原人类对手会作出的反应。能力未核实前，优先采用完整对局替换或可验证的前缀重建，不把任意 replay takeover / snapshot restore 写成现成能力。

## 3. 需要限定、修正或暂不直接接受的建议

### 3.1 候选最优选择不是严格的能力上界

原稿强调候选集合的重要性，与已有方案相容；本项目此前提出的候选选择判别实验还需要更严格的措辞。

在固定决策时刻、有限候选集、指定己方续局策略、指定对手与采样条件下，分别执行候选所得的比较，称为**离线诊断参考**。若选择器使用完整隐藏状态或未来结果，就明确标注为乐观参考 oracle，不能部署为合法策略，也不能代表合法观察下可达的能力。

从带噪声估计中选最大的结果还会带来选优偏差。应报告每个候选的采样量与不确定性；需要验证参考选择的效果时，使用独立评估样本，而不是重复引用用于选优的最好结果。

若未观察到提升，只能说“在本次候选、介入时机、续局策略和样本中没有发现增益”。不能据此严格证明没有可学习的改进：其他候选、稍后介入、更合适的续局策略或模块交互可能改变结果。若观察到提升，也只说明值得进一步研究；还要检验合法信息是否足以作出选择，以及接入完整闭环后是否保留收益。该边界进入 [方法论](methodology.md)、[评测](evaluation.md) 和 [实验模板](../templates/experiment.md)。

### 3.2 “第一个学习模块做方案排序”保留为默认候选

排序模型有清晰接口，通常容易与规则比较，适合作为备选路线；原稿本身也将其称为默认选择。它不应覆盖瓶颈诊断：若主要失败是命令覆盖、观察丢失或建筑堵路，应先修对应问题；若参数搜索已经足够，暂不训练模型。

采纳到 [方法论](methodology.md) 的路线选择条件。进入学习实验前写明标签来源、候选覆盖、推理时合法输入、简单基线与完整对局接入方式，不能靠“比端到端简单”免除验证。

### 3.3 势函数塑形只采纳有条件的理论依据

已检查 [Ng、Harada、Russell 的原论文](https://people.eecs.berkeley.edu/~russell/papers/icml99-shaping.pdf)。其策略不变性结论是在所述 MDP 与正则条件下，对符合势函数差分形式的奖励变换成立。它不是任意奖励设计、任意训练算法或实战提升的保证。

因此 [方法论](methodology.md) 只把该方法列为可选研究项。使用前必须说明状态与任务建模、折扣、终止/截断处理；变长宏动作的时间跨度需要单独推导一致的实现。不能直接用单步公式为部分可观测输入、变化中的对手、奖励裁剪或有限样本神经网络训练提供保证。正式验收继续使用原任务结果，而非塑形奖励。

这也不意味着非势函数奖励在特定任务里必然失败；应明确它没有获得上述一般保证，并以实际任务验证其效果。当前不引入奖励模块或训练依赖。

### 3.4 Supalosa 可作为对照候选，不能直接继承实力结论

已检查 [Supalosa 仓库 README](https://github.com/Supalosa/supalosa-chronodivide-bot/blob/master/README.md)。作者确实把项目定位为面向新玩家的稳定、性能良好的对手，而不是复杂竞技型 AI。这里核实的是**作者定位**，不是本项目测得的强弱或稳定性。

采纳到 [环境审计](environment-audit.md) 与 [评测](evaluation.md)：可将其列为外部对手候选，接入前固定版本并检查引擎兼容性、规则、信息权限和实际可运行性。不能以它单独代表全部对手分布，也不能据此假定其胜率或必然可战胜。

### 3.5 人工案例数量、训练日程和晋升门槛不直接照搬

原稿的“十几到几十个人工案例”可理解为发现问题的起步量级，不是可靠性定理或固定交付数量。案例数量随机制覆盖与新增故障而变化；估计小幅胜率提升需要另一套样本设计。

同样，“完整对局才决定正式保留”适用于竞争力晋升，不要求每个日志修复或已验证的指令正确性修复都证明统计显著胜率提升。基础修复按正确性证据与适当整局回归验收；算法增益才承担相应的竞争力声明。实验、样本与检查应与结论相称。

原稿里关于 100 局近似区间的例子仅适用于相应独立胜负假设，不能成为配对、混合地图或多训练种子设计的通用预算；本仓库不据此规定固定局数。

### 3.6 引用过的 API 说明仍需要版本化核实

原稿对回放限制的谨慎态度值得保留。当前 [官方 API 文档](https://www.npmjs.com/package/%40chronodivide/game-api) 也明确将回放动作描述为尝试执行的输入，并列出兼容性和支持范围限制。但在线 README 会变化，引用它不能替代锁定包内的类型、说明与运行验证。

正式 API 事实统一落在 [环境审计](environment-audit.md)，来源元数据落在 [api-provenance.json](references/api-provenance.json)。本审阅不自行确定“最新版本”，不根据文档存在某个名词推断有种子重置、指定出生位置、中途接管或完整状态恢复。
