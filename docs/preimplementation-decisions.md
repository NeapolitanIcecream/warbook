# 前期分析收束：现在决定什么，什么必须由对局回答

更新：2026-09-15。本轮目标是在启动 bot 实现前消除会改变路线的关键未知，并提供可复算的分析、公开输入来源与最小实验设计。不是要求把所有可能的游戏机制先研究完。

## 1. 本轮交付及证据级别

| 交付 | 新增价值 | 证据级别 |
| --- | --- | --- |
| [接口契约](interface-contract.md) | 把观察、任务、请求与实际效果映射到公开 API，处理结束状态和过期决策 | 固定源码检查；其中轻量探针仅为提取方法 + mock，不是真实引擎 |
| [对手与数据](opponents-and-data.md) | 固定公开版本，调查可用对手、地图标识与回放来源，检查接入风险 | 公开来源检查；Supalosa 已做深路径加载/构造探针，未调用生命周期或实战 |
| [首批实验](first-experiments.md) | 针对仍可能失败的设计给出区分原因的实验卡和伪改进反例 | 设计与分析案例，未跑游戏 |
| [统计预算](statistical-budget.md) | 区分直接对战与对手池增益；量化样本需求、选优偏差与对手混合偏差 | 已执行的概率模型计算，不是游戏数据 |

旧的 [环境审计](environment-audit.md) 与 [来源清单](references/api-provenance.json) 保留静态审计范围；不要把本轮 mock 探针或统计计算追记为旧表所有运行项目均已通过。

## 2. 可逆的起步选择

以下是为了让下一项实施可执行而选定的**工程默认值**，不代表最终赛制、最优参数或用户已指定的国家偏好。

| 项目 | 起步选择 | 理由与更新条件 |
| --- | --- | --- |
| 引擎基准 | API 0.79.0，对应引擎 0.84；实施时精确安装并记录锁文件 | 与已审计来源一致；升级时重查相关语义 |
| 部署 | 外部 Node 控制器，首个 bot 使用同步规则决策 | 避免首轮同时引入模型服务与 lockstep 数值问题；异步推理由具体需要触发 |
| 对局 | 正常开局、两个敌对玩家、一个国家镜像 | 保留经济和完整任务；首局必须检查实际联盟状态，而非相信配置名称 |
| 国家候选 | Americans 镜像用于工程试跑 | 官方例子中已有该国家字符串；实际可用性在资源加载后核实，不推断其最容易或最平衡 |
| 首个地图候选 | `mp03t4.map` 用于工程试跑 | 官方 API 示例明确使用；不是已认证的公平 1v1 评测图，见对手与数据调查 |
| 开局选项 | 首次接线参考官方示例的 10000 credits、unitCount=10、gameSpeed=5、crates=false、superWeapons=false、shortGame=true、mcvRepacks=true、buildOffAlly=false | 仅用于减少与示例的差异；首局记录真实生成物与终局规则。竞技配置另行选择，不将其称为标准人类赛制 |
| gameMode | 初始化后枚举该地图可用模式，选定并记录模式 ID 与含义 | 不在资料不足时硬填数字，也不把某个数组下标当永久语义 |
| 观察 | 工程诊断暂用接口契约的 `api-shroud-v0` | 它有明确披露的特殊可见性限制，仅支持受限诊断；正式合法信息目标另行验证，不按 SC2 当前视野裁剪 |
| 决策调度 | driver 暂每 3 个 simulation tick 同步统一决策，回调只登记句柄/边界；记录实际观察/请求/生效时刻及每单位指令量 | 3 tick 是可修改的起步值，不是最佳频率；不从 API 调用次数推断 APM，不并存两套决策循环 |
| 初始化 | 记录实际出生位和可获取的初始化来源，交错或随机安排版本 | 公开 API 没有固定 seed/起点；验证控制后才使用精确配对术语 |
| 运行存储 | 配置和证据摘要入 Git，大日志/replay/资产在忽略目录或外部存储 | 单个 manifest 加可追溯文件足够，不先建数据库和仪表盘 |
| 对手接入 | 优先自有最小基线，再接版本固定、信息条件已核对的外部对手 | 现成示例可能有版本/联盟/隐藏信息问题，不能原样当公平基线 |

这里只确定首场工程运行的候选设置。最初几局检查动作、状态与兼容性，不估计总体实力。最终地图池、各对手权重、具体目标玩家水平和实战操作限制，将在首轮观测与公开输入核验后冻结；不得从工程试跑成绩推导泛化结论。

初始单位数与 shortGame 等选项改变任务，不应在后续策略比较中悄悄切换。若改为无额外战斗单位的开局，需要先确认当前引擎的 unitCount 语义和 MCV 生成条件，再重建对应基线。地图和规则选项固定后，才生成训练/晋升/最终留出的清单。

## 3. 现在不值得提前绑定的决定

| 决定 | 现在不定的原因 | 最小决定性证据 |
| --- | --- | --- |
| 首个 RL 模块、算法和网络大小 | 还没有真实失败分布和同接口简单基线 | 已确认瓶颈、候选改进空间与初步闭环比较 |
| 最终地图/对手权重 | 地图属性与可用对手尚需实际加载/接入核对 | 不同布局、打法与信息条件下的可运行记录 |
| 训练小时数或 GPU 预算 | 采样成本可能主导，模型大小无法决定成本 | 开局/交战端到端吞吐和多次小规模学习曲线 |
| 精确 fork、快照格式和内部引擎改造 | 公开 API 不提供，首场完整局不依赖它 | 一个局部比较因不可控噪声明确受阻，且分叉成本合理 |
| 自定义微操场景生成器 | 尚无已观察的、需要隔离的真实机制问题 | 真实前缀/故障与明确可被否定的解释 |
| 联赛、Elo 服务或通用统计平台 | 对手少且还没有对局证据 | 简单文件与分项报告无法支持具体比较时再增加 |
| 全部特殊单位的公平观测实现 | 需要当前引擎行为与比赛信息协议 | 使用到该机制的首个实验；此前明示覆盖限制 |

这些是待实证的问题，不是等待更多泛泛分析或默认要求用户再次批准的事项。进入相应工作时采用最小安全实验获取证据。

## 4. 足够开始实现的研究循环

1. 精确安装已审计版本，接入用户本地可用 MIX 路径，运行普通地图敌对双 bot。
2. 用 [接口契约](interface-contract.md) 分开 actor 观察、请求、仲裁、实际效果与裁判记录。
3. 区分正常游戏结果、runner 停止、超时和未知结束；若 API 不足以确认，保留未知，不编造赢家。
4. 检查一段生产与一次移动/攻击，保存完整运行与可播放 replay。
5. 从真实失败选一张相关 [实验卡](first-experiments.md)，比较最便宜的竞争解释，再接回整局。

首场 run 使用现成接口即可；避免把实现公共库、完整观测模拟器或分叉平台作为开局条件。需要资源路径时，只取得运行必需的信息，不扫描用户其他项目来恢复历史架构。

## 5. 前期分析的完成与重开条件

本轮可完成的是：方案能映射到现有接口、关键未知有针对性实验、公开输入有明确来源、统计比较与选优风险能复算、文档区分事实与假设。不能仅靠分析确认：AI 强度、真实动作效果、回放一致性、初始化独立性、玩家等价观察、吞吐或算法收益。

当以上设计足以支持首局后，继续扩写文档的边际价值很低。下一步转为最小完整运行；只有新接口版本、实际行为与文档冲突、明确不可获取的数据、或实验无法区分原因时，才重开对应分析。下一份重要产物应有真实运行证据。
