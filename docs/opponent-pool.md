# 小型对手池与共同演化：下一轮执行方案

状态：2026-09-15。方案先按用户要求完成推演，随后于 21:07 获准执行。首轮已完成冻结接入、骚扰与守势路线试跑、固定池比较；M0 保留为默认主线，counter 保留为实验对手，详见 [执行进展](progress.md)。下文保留开工前的方案、假设和起步默认值，条件推演不作为已运行结果。

## 1. 已达成的共识与当前事实

目标是让可玩的主线 AI 持续应对新的真实威胁。采用 **定期评测、择优吸收、保留专长** 的节奏；共同演化指主线与挑战者交替改进，可以从规则和参数开始，不要求先训练模型。

已核对的事实：

- 当前主线为 Warbook 0.1.4，规则策略；真实对战、玩家入口和完整回放已通过，见 [执行进展](progress.md)。
- 固定客户端 0.83.3 的常规完整 AI 入口是 `Easy/Beta`，由 `SupalosaBot` 实现；另有 `Dummy` 占位。源码枚举中出现其他难度名不等于已有对应完整 AI。
- [官方构建适配器](../src/official-opponent.ts) 和 [npm 对手适配器](../src/opponent.ts) 都接入 Supalosa 的不同构建。它们可暴露不同缺陷，但不能据此计作两个独立策略家族。[官方更新记录](https://chronodivide.com/patch-notes.html) 也明确记录了单人 AI 的 Supalosa 来源。
- 现有 `baseline/cohesive/guarded/pillbox/sentry/crush/tempo/combined` 是同一代码中的实验模式，尚未完成打法多样性认证，也不是各自冻结的历史版本。
- 三张已用地图 `mp03t4.map`、`mp06t2.map`、`mp29u2.map` 均已参与开发。换一批对局不能把这些地图重新称为未见地图。

下一轮的第一目标是验证一个挑战者是否产生有价值的新压力，再改进主线；不是先把所有设想的路线实现一遍。

## 2. 池的组成与更新责任

| 角色 | 起步规模 | 用途与更新方式 |
| --- | --- | --- |
| 玩家主线 M | 1 个发布版本，另有未发布候选 | 追求综合表现；候选通过相应验证后替换玩家版本 |
| 特色挑战者 C | 先做 1 个，再按证据扩至 2 个；起步上限 3 个 | 寻找主线弱点、保留不同反应；一次只修改一个挑战方向 |
| 冻结历史 H | 起步保留 M0，之后最多保留 2 个活跃历史对手 | 检查遗忘，保存仍能暴露独特弱点的版本；退出活跃池后仍保留源码与复现记录 |
| 外部锚点 A | 固定 npm Supalosa；官方构建作为补充检查 | 保留不随自家策略一起修改的参照。同源构建增加时不自动增加该家族的总权重 |

这些是可加载的版本，不是需要一直运行的进程。默认串行比赛；结束立即释放游戏实例，候选服务与测试页面用完即关，维持现有玩家入口。

root Agent 负责路线、实验、版本保留和发布。用户只试玩并反馈；不要求用户调参、挑对手或审核实验。

## 3. 哪些共享，哪些必须冻结

开发时共享成熟的游戏依赖、合法观察、生产与命令执行实现；不同路线只增加必要的资源分配、目标选择和任务条件。记录不把共享代码误当成行为独立性。

一次比赛中的冻结单位应覆盖 **策略、观察转换、命令仲裁及其所用配置**。仅固定策略名字或一个参数文件，仍可能被共同底层的修改改变行为。

- 初始 M0 取 `v0.1.4`，对应 Git `68852328061240c50e622aae64cef7e9289af444`。后续观战入口修改未改变该策略。M0 是下一轮的增量对照；早期 `baseline` 继续作为工程历史，不直接充当未经审定的正式 B0。
- 引擎沿用 API 0.79.0 / 源码版本 0.83.3 / replay 标识 0.83。自家对手沿用同一观察和动作预算；对手 ID、实验路线名和裁判隐藏信息不能作为策略选择的输入。
- 每个版本记录来源 commit、构建方式、文件哈希、配置、观察/动作协议、父版本与本次改动。每局关联双方版本及现有 manifest、结果和 replay。复用文件与 Git，无需引入版本服务。
- 通用修复可以进入新的主线和挑战者版本，不能悄悄改写历史对手。若信息、动作或评分协议改变，则创建新的比较条件，按新条件重测双方并保留旧结果。

### 现有代码的具体缺口

[runner.ts](../src/runner.ts) 的 `--mode` 与 `--opponent` 当前从同一工作区实例化 `WarbookBot`；修改共享 `policy.ts` 会改变双方。`instanceof WarbookBot` 也承担了调度分类，不能直接假定另一个构建导出的类会通过它。[batch.ts](../scripts/batch.ts) 当前固定被评估方在首个槽位。现有 manifest 能追溯来源，但不会自动隔离双方代码。

下一轮先补最小的双方版本接入：

1. 从固定 Git 状态构建自家 Bot 包，覆盖上述行为代码；复用现有 esbuild，SDK 保持外部依赖并解析到同一份固定实例。生成包留在忽略目录。
2. runner 为每一侧显式登记类型、版本及调度接口，延续当前同步观察→决策→提交顺序，避免依赖不同构建间的类身份；外部 Supalosa 仍走已验证的原生适配路径。
3. 支持交换“被评估策略处于哪个创建/执行槽位”，并在结果中按策略身份归属胜负。它只平衡槽位和执行顺序，**不等于固定或交换地图出生位置**。
4. 先用同一 M0 的原接入与冻结包作少量完整局和兼容回放检查，发现包装造成的行为/调度问题就先修。普通新局没有相同初始化，不能要求两局逐 tick 一致，也不能把小样本 A/A 当作无偏证明。

这段改动服务于即将开始的具体对照；不扩成通用插件、联赛或分布式训练平台。若最小接入仍不能保持行为版本独立，先解除这一问题，再解释共同演化的比赛结果。

## 4. 挑战路线及其反证

默认先尝试 **矿区骚扰**：它改变攻击目标和兵力分配，与当前以正面坦克推进为主的行为差异较直接。第二条 **守矿反击** 只在第一条已形成压力，或新局出现相应失败时推进。两者目前都是待验证设想，不是已确诊的主线漏洞。

| 路线 | 最小变化 | 要看到的真实行为 | 不应继续沿原解释优化的情况 |
| --- | --- | --- | --- |
| 矿区骚扰 C-raid | 从合法接触中选择矿车/矿区目标，分出小队，避免被主力牵走；继续正常经济与生产 | 实际到达目标、攻击或迫使采矿中断，对手的防守选择影响后续局势 | 指令被覆盖、部队不能到达、目标始终不可见；先查执行/侦察，不直接增加奖励或宣布骚扰无效 |
| 守矿反击 C-guard | 为受威胁的矿区保留有限兵力，按接触变化回防与恢复进攻 | 可见威胁触发调动，矿区受损减少，之后仍能组织进攻并结束对局 | 仅无限囤兵/炮塔或拖到上限；生存时间变长不能替代完整局收益 |
| 预留第三路线 | 由前两条未覆盖的真实压力决定，例如空中压制或科技转换 | 能迫使主线作出前两条未要求的有效反应 | 只换名称、起始资金、难度或随机开局顺序，而关键反应相同 |

首次接触与进攻时点、资源投向、目标、兵力分配、受压后反应，只是行为诊断；不拼成可替代胜负的“多样性总分”。路线应能完成正常经济、生产和交战。测试其反应需会继续决策的对手，不能用录像后半段的固定指令冒充响应。

## 5. 一轮共同演化如何执行

每一小步固定其余条件。挑战者升级与主线升级分轮进行，避免同时移动的参照。

| 步骤 | 本步改变什么 | 产出与下一项决定 |
| --- | --- | --- |
| 0. 保留稳定版 | 仅补双方版本接入及必要记录 | M0 可继续试玩，双方行为来源独立且调度可解释；确认下轮条件与预算 |
| 1. 行为试跑 | C-raid 的一个最小策略变化，M0 固定 | 查看骚扰是否实际发生；有效则冻结 C-raid，无效先区分目标、执行、时机 |
| 2. 复现压力 | 不改双方版本，用新局检查代表性 | 保留实际失败或新反应；需要守势比较时再引入 C-guard；没有新压力就不急着改主线 |
| 3. 改主线 | 根据压力只改一个相关模块，挑战者固定 | M1 对 M0 的可解释增量；有必要时加入一个简单替代，例如全军回防与有限分兵 |
| 4. 固定池比较 | 双方代码、池成员、条件与权重均固定 | 同时重测 M0 和 M1，报告整体、切片、异常与代价；按诊断需要补挑战者间交叉对战 |
| 5. 保留与发布 | 完成比较后才更新池或玩家版本 | 分别决定挑战者入池、候选是否继续确认、主线是否发布；下一轮使用新的池版本 |

起步参数由 Agent 在运行前落到现有实验记录中；以下提供可执行默认值而非已冻结的统计验收预算：

- 先用 `mp03t4.map` 和 `mp06t2.map` 开发，`mp29u2.map` 仍作已见回归。国家 Americans 镜像、10000 资金、零起始军队，沿用现有固定引擎规则与每 3 tick 的自家决策间隔，记录引擎实际规范化后的配置。注意单局命令目前默认 `--units 10`，下一轮必须显式传 `--units 0`。
- 每条路线首批 4 次启动（每张开发图 2 次，平衡角色槽位），只判断动作与完整链路是否生效。随后按具体压力补新局；不要求首批已经有显著胜率。
- 当两个挑战者都具备价值时，起步开发比较池可取 `C-raid / C-guard / M0 / 固定 npm Supalosa`，四项等权、两张图等权。每个被评估版本在每个格子 4 次启动，共 32 次；M0 与一个 M1 合计 64 次。若只有一个有效挑战者，在看候选成绩前重新写明池与权重，不能用无效对手凑数量。
- 32 次/版本用于开发筛选，不足以自动确认细小增益。需要正式声明时，冻结候选后另设预算和查看节点，使用未参与选择的新证据。
- 保留现有 54000 tick / 单局 180 秒上限及进程超时；每次启动都记录正常胜负、未决、内部错误或外部故障。开发筛选分别报告正常获胜次数占全部启动的比例与各停止类别；归因明确的自身错误计失败，外部故障按事前规则处理，未决不作平局或静默排除。不能归因到某一方的错误先诊断，不能默认算给候选。正式得分及比较分母遵循 [评估协议](evaluation.md)。
- 普通未控种子新局不冒充精确配对。记录实际起点、创建时间、运行顺序和来源组；观察到初始化重复或批次效应时，先诊断相关性再解释小幅收益。

只运行能改变当前决定的交叉对战，不要求全池两两打满。池、权重、地图或裁判规则变更后，保留旧比较，并重测当前比较双方。不得相减不同池上的总分。

## 6. 两种保留决定必须分开

### 挑战者是否入池

一个挑战者值得保留，需要：正常可执行、行为有差异，并能暴露新的失败或要求不同的有效应对。它可以综合胜率一般；仅擅长惩罚某种漏洞也有价值。反之，胜率高但行为和现有对手重复，不必占一个活跃位置。

两两对战可能形成 A 克制 B、B 克制 C、C 又克制 A 的关系。因此同时保留关键对阵与地图切片，不依赖一个总排名判断哪些专家可删除，也不将只战胜上一版视为持续进步。

连续两轮局部修改既没有行为变化、也未排除原因或形成新压力，就暂停该路线，检查更早的介入时机或换一个机制。归档重复/失效版本及原因，保留复现信息；不为了降低主线难度而移除仍有效的克制者。

### 主线是否发布

功能修复和综合棋力提升分别说明。修复已复现的观察/执行错误，可在相关回归通过后发布；声称综合增强，则需要固定池完整局证据及主要切片的代价说明，避免只针对最新挑战者优化。

新出现的内部崩溃、泄漏、无法正常结束或玩家操作链路损坏，应先修复。战术切片上的收益与损失按运行前写明的权衡判断，不能要求每个对手都严格上涨；证据含糊就保留 M0 供玩家使用，继续有判别力的工作。

保留原战略的正式 B0、固定 `D_target` 和约 +10 个百分点目标；以预定 95% 区间下界高于 0 确认正增益。M0 是增量对照，开发池不是自动冻结的正式目标分布，也不能把早期弱 `baseline` 的差距追认为正式达标。

## 7. 策略如何吸收到主线

| 发现 | 处理方法 | 必须解释的交互 |
| --- | --- | --- |
| 通用正确性修复或可复用能力 | 合入新版本并做相关回归 | 观察与命令语义是否改变；旧版本保留，协议变化时重测双方 |
| 有条件才有效的战术 | 合入策略及其触发、退出、资源和单位归属条件 | 回防是否抽走进攻主力，骚扰是否挤占必要补兵，任务切换是否反复覆盖命令 |
| 互斥开局或资源路线 | 保留为可选计划，以合法侦察及已知规则选择 | 不能依赖实验给出的对手路线标签，也不能每帧切换导致生产和兵力承诺失效 |
| 有独特克制关系的专家 | 留在对手池；有需要时再比较主线的计划选择或整局策略混合 | 完整组合自身需要评估，不能用事后“每局挑赢家”模拟可部署能力 |
| 将来的学习模块 | 在确有选择问题时比较规则、搜索、监督或局部 RL；蒸馏按同样规则验收 | 模型参数直接平均或代码合并没有自动保留能力的保证，训练和部署信息必须合法 |

合并的时间由上述证据决定。Git 分支可以合并代码，策略是否值得发布由整局行为与结果决定。

## 8. 一次完整推演：结果会怎样改变决定

**以下都是条件推演，没有对应的新对局结果。**

1. **C-raid 没打到矿车就输了。** 若命令被主力任务覆盖，先修挑战者控制权；若执行成功但来得太晚，比较介入时机。当前证据不支持“主线已经会守矿”，也不支持“骚扰路线无价值”。
2. **C-raid 反复使 M0 矿区停工，并完成正常胜局。** 先区分主线没有观察到矿区接触、没有选择回防，还是回防命令未生效。前两项与后一项需要不同修复，不立即把问题归为缺少学习模型。
3. **M1 全军回防击败 C-raid，却失去进攻时机。** 用冻结的其他对手检查代价；若代价成立，比较有限分兵和任务退出条件，而不是把更多回防代码直接并入试玩版。
4. **有限分兵改善整体，仍被某个历史版本克制。** 查看该切片和不确定性；若只是不同路线间的克制，保留历史对手并按既定权衡选择。不能因总胜率低就删掉它，也不能要求所有克制关系消失才继续。
5. **M1 对最新池得分更高。** 用同一池重测 M0；如果 M0 也同幅度上涨，优先解释为池变化，不能记为 M1 的策略收益。正式确认还要使用未参与候选选择的证据。
6. **共同底层修复令所有模式同时提高。** 新建各版本身份，收益归于共享修复，不宣称各路线分别学会了新能力；冻结旧对手仍保留原行为。
7. **自家互战很好，换外部条件就失败。** 回到观察、执行和对手反应查共同盲点。自我对战局数不能替代外部挑战；这批失败一旦用于修改，就记录为开发来源。

## 9. 共同盲点与独立证据

自家对手共用表示和执行器，可能一起漏掉某种合法威胁。Supalosa 作为外部锚点仍有帮助，但它也不是高手标尺，且原生信息条件与自家协议未完全对齐；相关结果单列，不把其特权信息用于自家策略或合法示范标签。

区分三个边界：

- **开发池** 可以反复用于诊断和选择，对手会间接被适应。
- **冻结候选后的新对局** 可以检验该产物在既定条件下的表现；它不自动构成跨新地图或新打法的泛化证据。
- **预留的新地图/对手来源** 服务于相应范围的最终检验。下一轮从固定引擎可用地图中按布局选定新来源，先检查加载兼容性，不按候选胜率挑选；已有三图不充作新来源。留出结果指导修改后记录暴露，后续不再称其未见。

完全本地开发继续有效。真人试玩反馈是补充压力来源，不把用户参与设为每轮的前置条件。公开真人回放需先核对引擎/规则兼容性；仅解析、观看或固定指令重放不能冒充可响应的对手。没有足够独立来源时收窄结论，不用更多同源版本凑足“家族数”。

## 10. 下一轮的交付边界

进入下一轮执行时，按本页直接推进：保留可玩 M0 → 最小双方版本接入 → 一条实际产生差异的挑战路线 → 一个真实弱点的解释与候选 → 固定池比较 → 依证据发布或保留稳定版。

交付应包含一份简短比较记录、双方版本、正常胜负与异常计数、代表性完整回放和下一项决定。有效挑战者的形成、排除一个关键解释，以及有证据的主线修复分别报告；不提前承诺每轮都会提高胜率。

时间以实际接入、诊断、完整局与修复耗时滚动预测。首轮已有秒级单局记录，但不同挑战路线可能拖长终局，且研发耗时不能由单局耗时推算。默认控制本机资源占用；达到既有结构/性能检查触发条件时，做必要改善后恢复主线。

本方案已给出起步路线、对照单位、样本安排、失败分支和保留规则。新留出地图的具体 ID、构建产物哈希及实际预算在下一轮运行前由 Agent 按可用环境落定，不要求用户作技术决策，也不重复开展泛化预研。
