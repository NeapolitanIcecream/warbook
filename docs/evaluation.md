# 评估与证据规则

本文件定义如何判断一次改动是否有效。**当前仓库只有设计文档，没有运行结果、基线成绩或已通过的能力验证。** 下述流程和默认值是建议；API 事实与待测事项以 [环境审计](environment-audit.md) 为准。设计参考了 [GPT-6 Pro 原文](references/gpt-6-pro-original.md)。

基本闭环是：**完整对局发现问题 → 局部实验区分原因 → 独立完整对局判断是否保留改动。** 评测规模应与结论相称，不要求先建通用研究平台。

## 1. 下一次实验最少需要什么

1. 一个能运行正常完整对局的基线，锁定其代码、引擎、地图、规则和对手版本。
2. 正常开局的少量对局，记录实际初始条件、胜负/平局、超时、异常、回放位置与关键失败时刻。
3. 从失败中提出一个机制假设和至少一个替代解释，只改一个相关模块。
4. 用相同评分协议，在相同地图与对手分布上跑基线和候选的新对局；不能控制的初始化因素如实记录。
5. 填一份 [实验记录](../templates/experiment.md)，给出结果、反例和下一步。小批量结果可以帮助定位故障，不能自动证明细小胜率提升。

只有当一个近期实验明确需要时，才增加场景生成器、分叉适配器、自动报表或训练基础设施。机制审计与完整基线建设可以并行；每解决一项局部问题，就尽早接回完整对局。

## 2. 四种测试用途与可用能力

| 用途 | 如何取得案例 | 可支持的结论 | 不能升级成的结论 |
| --- | --- | --- | --- |
| 机制测试 | 正常对局中的短指令实验，或经能力审计支持的受控设置 | 指令、观察、寻路、攻击等实际语义 | 战术或战略更强 |
| 真实局部诊断 | 回放分析、完整新对局中的模块替换；能力允许时重建前缀 | 某种真实失败的原因及局部改善 | 全部分布上的棋力提升 |
| 受约束扰动 | 在已验证的设置能力内，变化某个场景家族的条件 | 改进对哪些条件敏感 | 这些人工条件具有真实发生频率 |
| 完整对局验收 | 正常初始化，从开局运行到预先定义的结束条件 | 指定地图、对手与操作限制下的表现 | 对所有地图和所有玩家都有效 |

受约束扰动是一种**测试模式**，无需为其另建一套平台。它可以通过改变合法开局配置或对手策略实现；若要直接改中途状态，则需要另行验证对应适配器。

能力边界分三档：

- **现有公开接口支持的方向：** 正常创建并推进新对局、导出回放、分析兼容回放。具体版本和本地运行仍需验证；公开示例存在不等于本仓库已经运行成功。
- **需要适配器验证：** 通过正常开局和指令前缀重建局面，再将控制交给能响应局势的策略。必须验证初始化、动作执行、双方记忆和状态一致性；没有这些证据，只能称为相近局面比较。
- **未发现现成公开支持：** 任意 snapshot/fork/seek/replay takeover。当前审查也未发现 `createGame` 公开暴露 seed、固定出生位或每人独立起始资金；回放中的 `getPlayer` 为只读。不要将这些能力写成实验的既有前提。

没有精确分叉，仍然可以做回放诊断、完整对局模块替换和相同配置分布下的比较。若出生位由引擎分配，就记录并分层报告实际位置，不声称已交换或固定位置；若初始化未能重现，就不声称精确配对。

## 3. 先判定错在哪一层

| 类别 | 证据示例 | 最小区分实验 |
| --- | --- | --- |
| 观察错误 | 合法可知的敌情没有进入表示；或隐藏信息经事件、ID、掩码泄露 | 比较合法观察、内部表示和引擎真值，追踪信息来源 |
| 执行错误 | 选了撤退，但命令未生效、目的地不可达或被另一模块覆盖 | 记录意图、发送命令与状态后置条件；暂时隔离控制权 |
| 评估错误 | 输入与执行正确，却高估接战收益或低估增援 | 比较预测与实际结果；替换预测器，保留其他模块 |
| 决策错误 | 已预测守矿失败，仍因错误目标或预算选择撤退 | 保留预测，替换目标、候选方案或选择规则 |
| 评测错误 | 坦克存活但矿区失守，测试仍判守矿成功 | 修改任务成功条件，单独版本化并重测基线 |

一个失败可以有多个原因。先检验最便宜、最可区分的解释；必要时做两个模块的交叉替换。不能因为“学习模块接上后仍输”就认定算法不行，也不能把执行修复产生的收益记为决策学习收益。

## 4. 场景审查与评测器故障注入

每个新场景家族都说明以下条件，不要求每个样本写长报告：

- **规则与来源：** 位置、通行性、所有权、生产和资源状态是否合法？来自哪场对局或哪段合法生成过程？引擎允许摆出一个局面，不证明正常对局能到达它。
- **代表性：** 它在什么地图、阶段、对手与任务中有意义？失败挖掘集可以刻意偏向困难案例，但不能冒充目标对局分布。
- **信息：** 策略只使用按赛制允许的观察和历史推断；引擎真值可以用于诊断标签，但超出合法观察的真值不能流入执行策略或在线搜索。
- **目标与时间：** 测守矿、争取时间、交换比还是最终胜负？时间窗口是否短到敌军尚未接触目标就被判成功？诊断指标分别报告，避免加权总分掩盖机会成本。
- **敏感性：** 是否存在不同方案可能产生不同结果？已必胜、已必败的案例可以保留并标注，但不能仅凭它们的胜负证明某个模块有决策收益。

对评测器实施有针对性的破坏，检验它是否能发现问题：

| 对照或故障 | 应检查什么 |
| --- | --- |
| 不发新命令 | 记录已有命令、自动索敌和其他引擎默认行为；此基线不等于无行为，不能把其收益归给学习模块 |
| 只按时间行动、不读局势 | 所谓观察或适应能力测试是否仍能被固定剧本解决 |
| 屏蔽有关敌情、禁用侦察 | 在确实需要该信息的案例家族中，结果是否变化；隐藏状态相异但合法观察历史相同的局面，不应泄露答案 |
| 禁用目标选择、撤退模块或增加命令延迟 | 在预期敏感的条件下能否检测到行为及结果变化 |
| 一致重映射实体 ID 或调整观察列表顺序 | 策略是否依赖无语义的编码特征；目标引用也必须随 ID 一起映射 |

故障不必在每个案例中降低成绩，简单策略也可能是最佳方案。如果预期敏感的一整类测试完全不变，应先检查假设、测试覆盖与故障是否真的生效。地图镜像不一定等价，需先验证地形、方向和寻路条件。

人类优先检查新失败家族，并将“出口被堵”“两个模块争抢同一单位”“结束过早”等发现转为可执行检查。非传统打法本身不是错误；行为优劣仍需结果证据。[SMACv2](https://arxiv.org/abs/2212.07489) 对开环策略的发现，是测试上述敏感性的研究依据，不是本项目已经复现的结果。

## 5. 真实轨迹、扰动与标签

回放片段至少关联原始对局、引擎/地图/规则版本、时点、合法观察历史、任务目标和实际指令效果。需恢复局面时，单位、坐标和血量并不足够：当前指令、攻击阶段、弹丸、队列、生产进度、信息历史及控制器记忆都可能影响后续。

如果将来验证了分叉能力，不同候选应从同样合法历史建立各自记忆，不能直接复制另一个模型的隐藏状态。分叉后对手必须继续响应局势；继续播放原录像后半段的指令，只能标记为固定动作序列测试，不能当作响应式反事实对局。

扰动按家族记录：来源、改变的变量、合法范围、保持的条件、对手策略、目标、结束规则和适用结论。例如从守矿失败出发，分别变化接敌方向、增援时间或可用部队，不同时任意改变所有条件。未经验证的中途修改不能称为真实状态分叉。对强策略产生的新局面，定期补充开发案例；冻结测试不随候选表现悄悄改写。

比较候选时还需固定或说明己方干预后的续局策略、任务持续时间与记忆处理。有限候选的离线选优受这些条件及采样噪声限制；用一组数据选出最好方案后，若要声称其效果，使用独立样本评价并报告不确定性。无提升只说明本次条件下未发现收益，不能证明没有可学习空间。

**一条只执行了方案 A 的轨迹，只提供 A 的实际结果，不提供 B 的结果，也不证明 A 导致了最终胜负。** 可监督已执行方案的结果预测。其他方案的标签应区分经验证的干预结果、带不确定性的专家判断，以及明确假设与适用范围的模型预测/伪标签。模型预测可用于探索或训练，但须独立验证，不能据此声称已经观测到引擎反事实结果；相近局面的结果也不能伪装成精确反事实标签。

## 6. 开发、晋升与最终留出

| 分区 | 用途 | 信息使用规则 |
| --- | --- | --- |
| 开发集 | 反复调参、诊断、训练与故障回归 | 可以查看细节；成绩不作为独立泛化证据 |
| 晋升集 | 按固定流程比较候选与现行基线 | 可反复用于工程选择，但长期使用会被间接适应，不再声称完全未知 |
| 最终留出 | 在明确里程碑上验证冻结候选的能力声明 | 不用于每轮调参；使用其失败指导修改后，记录暴露并将相关案例移入开发或晋升资产 |

按完整对局/来源分组切分；同一录像的邻近片段及其扰动属于同一来源组。泛化声明涉及地图或对手家族时，也应按对应家族留出，只换样本 seed 并不足够。最早可用清单标记分区，无需独立数据服务；最终留出规模随目标和运行成本确定。

候选代码、训练数据、场景生成方式、评分规则与对手版本分别记录。**评分或结束规则变化后，旧基线和候选都按新协议重跑；不直接相减跨协议分数。** 测试中的已知错误可以修复，不需要增加用户审批步骤；修复与策略改动分开记录和比较。

## 7. 完整对局报告与保留决定

实验前写明地图/规则/国家范围、对手及权重、合法信息、指令频率/延迟与推理预算、主要结果和终止规则。正常胜负、平局、游戏超时、bot 崩溃和运行器故障分别记录；提前决定如何计入汇总。不能静默丢弃候选输局或崩溃后重跑至获胜；确属外部故障的重跑需保留原因和原记录。

- 固定对手池保存简单可靠基线、历史版本和不同打法，更新挑战池寻找当前漏洞。比较版本时固定汇总权重，并报告地图/对手切片；总胜率上涨可能只是多打了弱对手。
- 能控制相同初始条件时使用配对比较；不能控制时使用相同配置分布、交错运行顺序和实际条件记录，报告为分层或非配对比较。相同 seed 也不保证两条不同轨迹的未来随机事件一一对应。
- 报告实际局数、效应大小、区间及重要退化。重采样等方法应以独立对局或来源组为单位，同一前缀的多个分支不能冒充独立样本。没有足够独立样本就描述结果，不用精美区间掩饰信息不足。
- 一个固定模型的多场评估，与多个独立训练运行是两回事。前者检验该产物的表现，后者才支持训练方法稳定性的判断；训练 seed 与未必可控的引擎初始化分开记录。
- 预定预算和查看节点，避免反复试到“显著”才停止。近似独立二元胜负在胜率约 50% 时，100 局的常用 95% 区间半宽仍约 10 个百分点；该量级不能直接套到相关、配对、含平局或反复筛选的结果。
- 引擎、地图或规则变化时，重新检查兼容性和关键语义，并在新版本上重测双方。对手分布改变时，分别报告原目标与新目标下的成绩，不把分布漂移记为策略收益。

晋升判断取决于预先声明的目标：消除可复验的执行错误可以支持工程修复，但不等于证明棋力提升；局部方案更好但整局退步时，应保留诊断结论、继续修正，不能宣布 AI 更强。小样本下结果不确定，可以继续做最有区分力的实验，无需机械地扩充到一个固定局数。

外部对手可考察 [Supalosa bot](https://github.com/Supalosa/supalosa-chronodivide-bot)，先固定版本并核查兼容性、信息和操作条件。它只是对手候选；作者定位与外部声誉不等于本项目测得的实力或稳定性。

[多智能体博弈研究](https://arxiv.org/abs/1711.00832) 支持关注训练对手过拟合；[RL 统计评估研究](https://arxiv.org/abs/2108.13264) 支持报告不确定性。这些原则不要求第一版实现完整 league、Elo 服务或复杂显著性框架。先保留原始完整对局证据，采用与样本和问题相称的比较。
