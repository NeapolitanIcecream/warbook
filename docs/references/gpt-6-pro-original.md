我的核心判断是：**这次首先要重建的不是策略代码，而是“什么算有效证据”的标准，以及围绕它工作的开发闭环。**

你之前的路线——让 Codex 写 heuristic、训练小模型、生成场景检验效果——各个环节本身都可能有用。问题在于，倘若**方法设计、场景设计、评价指标和结果解释来自同一套未经校验的假设**，这个闭环完全可能不断产出“进步”，却没有提高实际游戏能力。

我建议把顺序改成：

**真实引擎与信息规则校验 → 一个能打完整局的简单 AI → 从真实对局提取失败 → 用局部实验辨别原因 → 有针对性地引入搜索与学习 → 独立整局评测决定是否保留。**

这里最重要的变化不是“先 heuristic，后 RL”，而是：**真实对局提供问题，局部实验解释问题，独立对局裁决改进。**

我没有看到你的旧代码、场景和回放，因此不会断言之前具体错在哪里。下面是一套从零重建的方案；默认第一目标是在明确的信息与操作限制下，开发一个可靠、能持续提升的 Chrono Divide 1v1 AI，而不是先证明某种 RL 算法可行。

## 一、先把“开发一个 RA2 AI”改写成可检验的目标

### 1. 不要把“能赢一个 bot”当成“会打 RA2”

一个 AI 的强弱，总是相对于某种对局分布而言：地图、出生点、国家、规则、对手打法和操作限制。

可以把目标写成：

$$
J(\pi)=
\mathbb{E}_{x\sim D_{\text{target}}}
[\text{对局结果}(\pi,x)]
$$

其中，\(D_{\text{target}}\) 是你真正关心的对局分布，而不是场景生成器恰好容易生成的分布。

这要求项目开始时就明确：主要追求平均胜率，还是不能被某些常见打法轻易击败；主要对手是现有 AI、普通玩家，还是高手；是否允许超人类的操作频率；是否需要跨地图、跨国家泛化。

我的建议是，第一阶段缩小范围，但不破坏游戏的核心结构。例如，固定一个国家的镜像对局，选择少量地面地图，保留正常经济、生产、侦察与完整胜负条件，明确箱子、超级武器等选项。地图和出生点不能永远固定，保留一部分用于验收。

**缩小国家和地图范围，是控制研究范围；把经济、信息和战略目标全部删掉，再宣称学会了 RA2，则是换了问题。**

### 2. 区分三个不同的成功标准

**软件正确性：** 指令是否合法，单位是否真的执行，游戏能否稳定运行。

**局部能力：** 在某类交战、守矿或建造任务中，某个模块是否优于替代方案。

**整局竞争力：** 这种局部能力是否在目标对局分布上增加获胜机会。

三者不能互相替代。能稳定执行一套错误策略，不等于聪明；一个漂亮的微操实验，也不能自动证明整局水平提高。

更进一步，**“像人类”也不是最终标准。** 人类看出单位生成在障碍物里，是有效的场景审查；人类觉得某种打法“不像正常打法”，则还需要实战验证。要排除的是错误环境和虚假收益，而不是非传统策略。

## 二、先对 Chrono Divide 做“能力审计”，不要凭 API 名称推测语义

我核实到，官方 playground 确实提供了无界面运行、创建 bot 对局、推进游戏以及保存回放的示例。因此，项目可以直接以真实 Chrono Divide 引擎作为主要实验环境，而不必先自行实现一个简化战斗模拟器。

但“能调用 API”离“拥有可靠的 RL 环境”还差不少工作。

### 1. 第一份重要交付物应当是环境契约

建议建立一份版本化、可执行的环境契约：

| 需要确认的事项 | 应当用实验回答的问题                         | 对后续设计的影响     |
| ------- | ---------------------------------- | ------------ |
| 时间与执行顺序 | 一次 `update()` 推进什么？观察和指令分别发生在何时？   | 决策频率、延迟、奖励归因 |
| 指令语义    | 重复发同一命令、切换目标、移动与攻击交替，会产生什么实际效果？    | 微操控制器是否真的有效  |
| 信息边界    | bot 在每个时刻可以合法知道什么？事件、对象查询是否透露额外信息？ | 训练与实战是否一致    |
| 初始化与复现  | 哪些随机源可控制？同样的初始配置和指令能否复现？           | A/B 比较和失败重现  |
| 状态恢复    | 能否恢复完整状态、接管回放、从中途分叉？               | 是否可以做精确反事实实验 |
| 吞吐量与部署  | 加上真实 bot、日志和推理后，每秒能采集多少有效决策？       | 哪种训练方案负担得起   |

这里有几个特别容易犯的错误。

**第一，不要直接照搬 StarCraft 的观察模型。** 应当按 Chrono Divide 实际的黑幕、探索、特殊遮蔽和可见性语义定义观察，而不是把一个通用 RTS 的“战争迷雾模型”套上去。官方补丁记录中，黑幕计算、临时显形、移动、攻击和生产等行为都经历过修正，这也说明不能仅凭原版 RA2 的记忆确定当前引擎语义。([Chrono Divide][1])

**第二，不要把 API 能读取的信息自动当成合法输入。** 例如，官方示例会查询敌方起始位置；这是否符合你的评测条件，必须由赛制决定，而不是由“接口能返回”决定。

**第三，发出指令不等于执行成功。** 必须把“策略选择了什么”“适配层发送了什么”“游戏里最终发生了什么”分开记录。没有原生执行回执时，就通过后续状态变化检验后置条件。

### 2. 回放能力与状态分叉能力必须分开

我读到的 npm 文档提供了回放解析与兼容多人回放的逐回合模拟，同时明确说明：回放动作是尝试执行的输入，不代表执行成功；回放依赖引擎版本、模组与地图匹配；所描述的初版接口不支持 seeking 等功能。**这些文档不能证明任意快照恢复、任意时刻接管和分叉模拟已经可用。**([npmjs.com][2])

因此，不应一开始就把整个方案建立在“从任何回放时刻 fork 一百次”之上。先验证本地锁定版本究竟支持什么，再选择实验路径。

### 3. 部署位置会影响小模型的实现方式

官方文档区分了外部 sandbox bot 与集成进游戏循环的代码，并指出后者需要满足确定性要求，否则可能影响同步和回放。([npm][3])

所以要提前决定：模型是作为外部控制器生成命令，还是嵌入同步游戏逻辑。不能等模型训练完成，才发现推理数值、随机性或异步执行方式不符合部署要求。

同样，训练成本应从实测吞吐量推算：

$$
\text{采样时间}\approx
\frac{\text{需要的有效决策样本数}}
{\text{端到端有效决策吞吐量}}
$$

**小模型只意味着模型可能较小，并不意味着获取训练经验便宜。** 吞吐量必须包含初始化、游戏推进、观察编码、通信、推理和必要日志，而不是只测空环境的速度。

## 三、重新设计评测：合成场景是实验工具，不是默认可信的裁判

这是整个项目里最应该投入方法论工作的部分。

### 1. 一个场景“能运行”，远远不等于“能评价能力”

我会对每类场景提出五个问题。

**物理与规则是否合法？**
单位位置、通行性、射程、高低差、建筑出口、所有权、伤害与生产状态是否正确？

**状态是否具有合理来源？**
它是正常游戏中可以到达的局面，还是仅仅在编辑器里可以摆出来？如果刻意构造了非正常局面，它究竟用于测什么？

**信息是否正确？**
策略是否只拿到了按规则允许的观察？是否通过事件、对象 ID、动作掩码或全局统计偷偷获得了答案？

**目标是否正确？**
它测的是消灭敌军、保存部队、保住矿区、争取时间，还是整局胜率？这些目标之间是否可能冲突？

**结果是否对被测能力敏感？**
一个不观察敌人的固定脚本，是否也能拿高分？去掉被测模块后，结果是否几乎不变？

最后一个问题尤其重要。SMACv2 的研究发现，在旧 SMAC 的不少场景中，只根据时间步行动、忽略实际观察的开环策略，也能取得非平凡表现。一个看起来复杂的 RTS 基准，未必真的要求你以为它在测试的能力。([arXiv][4])

### 2. 把评测分成用途不同的四层

**机制测试，回答“我们是否理解引擎”。**
例如，某种单位执行一段移动、攻击、切换目标指令后，实际移动了多远、发射了几次、造成多少伤害。这里允许非常人工化的场景，因为目的就是隔离机制。

**真实局面的局部测试，回答“模块是否解决了实际问题”。**
从完整对局中寻找守矿失败、生产停滞、阵型拥堵、错误接战等片段。尽量保留其上下文，而不是只复制几个单位到空地上。

**受约束的场景扩展，回答“改进是否依赖偶然条件”。**
围绕真实局面改变接敌方向、兵力比例、增援时间、地形和对手行为。每种扰动都要有明确的合法性边界。

**完整对局验收，回答“AI 是否真的更强”。**
保留地图、出生点和对手组合，使用冻结协议比较候选与基线。

这四层不是谁替代谁，而是承担不同职责。**机制测试可以推翻一个实现，局部测试可以支持一种解释，完整对局才决定是否把改进纳入正式 AI。**

### 3. 给评测器本身写测试

不只是测试 bot，还要测试“测试是否有用”。

例如，准备一组有明确差异的对照控制器：始终接战、始终撤退、固定时序行动、简单血量阈值，以及经过人工检查的参考控制器。它们不必在每个场景中按同一个顺序排名，但评测应能在适当条件下区分其能力。

再做故障注入：故意让目标选择失效、屏蔽有关信息、增加命令延迟、禁用某个关键模块。假如这些变化在一整类测试里完全不影响结果，需要先调查测试为什么不敏感。

注意，**“不发新命令”也不一定等于“单位什么都不做”**。因此，必须明确基线包含了哪些引擎自带行为，而不能把这些行为带来的收益归功于学习模块。

可以做对称变换和扰动测试，但不要机械要求镜像结果完全相同：地图方向、地形和寻路的等价性，也需要先验证。

### 4. 人类应该审查因果条件，而不是当永久打分器

初期可以用十几到几十个经过人工检查的案例建立“可信案例集”。这个规模用于发现机制错误和表达问题，不用于证明胜率提升。

人类审查应该留下可执行的结论，例如：

> 这不是撤退算法差，而是撤退目的地被建筑堵住。
> 这不是交战预测错，而是两个 squad 同时控制同一辆坦克。
> 这不是守矿成功，而是场景结束时敌人还没来得及攻击矿场。

然后把这些结论变成断言、状态检查和回归测试。

**目标不是让人类永远替 agent 看录像，而是把人类指出的常识错误逐步转化为机器能够检查的约束。**

## 四、尽早做一个完整但简单的 AI，避免“只有实验，没有游戏”

不应先搭建一个庞大的研究平台，再等待几个月后第一场完整对局。

我会尽快建立一个最小完整基线：能够展开基地、维持基本经济与生产、放置建筑、形成部队、找到敌人、交战并正常结束比赛。策略可以粗糙，但每一步必须可观察、可复现。

从零开发自己的架构，不意味着不能使用现有 bot 作为外部对照。Supalosa 的项目明确将自身定位为面向新玩家的稳定、性能良好的对手，而不是复杂的竞技型 AI；它适合成为一个工程与对战基线，但不能单独代表最终竞争力。

### 1. 我推荐的架构是“可替换的分层控制器”

总体数据流可以很简单：

```text
真实游戏
  → 合法观察
  → 记忆与局势表示
  → 战略目标和资源分配
  → 小队任务
  → 单位控制
  → 命令仲裁与执行验证
  → 真实游戏
```

这里不要求每层都用机器学习。第一版甚至可以全部是规则。关键是每一层有明确输入输出，能够单独替换和比较。

### 2. 战略层：表达目标、预算和承诺，而不是直接发零散命令

战略层决定生产方向、经济与军备投入、扩张、守备、进攻目标和部队分配。

输出不应只是“去攻击”，而应包含：由哪支部队执行、需要多少资源、目标是什么、在什么条件下中止，以及何时重新决策。

经济规划需要考虑现金流与实际扣费规则；建造规划不仅要检查“这里允许放建筑”，还要检查放下后是否破坏出兵、采矿和后续扩建。

**基础设施是否正常工作，应当先于“生产哪一种最优单位”得到保证。**

### 3. 战术层：决定哪些部队能在同一时刻发挥作用

不要只用“双方总造价”作为交战评估。

建议显式表达：哪些单位能在接下来一段时间内到达并有效攻击，哪些单位被地形或友军阻挡，哪些在执行其他任务，敌我增援何时到达，撤退会丢失什么目标。

对于守矿任务，“保存最多坦克”和“最大限度提高获胜机会”可能不是同一件事。战术层必须知道自己在保护什么，而不是永远优化交换比。

### 4. 执行层：把意图变成稳定行为

这一层应处理单位控制权、目标失效、重复命令、超时、卡住、重试和紧急中断。

尤其要有**命令仲裁**：同一单位不能同时被经济、守备、进攻和微操模块来回争抢。还应有适度的承诺时间和切换滞后，避免局势估计轻微变化就不断反向操作。

不要凭其他 RTS 的经验假设某种“走打”指令序列一定提高输出。先测实际移动和攻击效果，再讨论优化。

### 5. 分层是调试工具，不应成为永久上限

分层会限制策略空间。因此，我会尽量只把合法性和可靠执行做成硬约束，把“应该优先保护什么”“何时进攻”等偏好留作可替换的决策逻辑。

如果候选计划中根本没有好方案，再强的选择模型也无济于事。届时应扩充计划生成能力，而不是继续调选择器。

同理，第一版没有必要让每个单位都成为独立 RL agent。既然一个玩家可以集中控制自己的单位，先使用集中协调的小队或实体策略更容易建立清晰的实验对照；是否需要分散控制，应由后续需求决定。

## 五、数据应优先来自真实轨迹；“真实状态”还必须包含历史

### 1. 先建立失败分类，再决定采什么数据

每次失败至少要能够归到一个可检验的层次：

| 失败类别 | 例子                    | 下一步应做什么     |
| ---- | --------------------- | ----------- |
| 观察错误 | 可获取的敌情没有进入局势表示        | 修观察与状态更新    |
| 执行错误 | 发了攻击命令，但目标或单位状态使其没有生效 | 做机制与执行测试    |
| 评估错误 | 知道双方情况，却错误估计交战结果      | 改评估器或训练预测模型 |
| 决策错误 | 知道会亏损，仍因错误目标选择接战      | 检查目标、规划与奖励  |
| 评测错误 | 单位活着，但守护目标已经丢失，仍被判成功  | 修改并重新校验评测   |

这个分类的价值在于：**不要让 RL 替 API bug、命令冲突或错误评分规则背锅。**

接着做“瓶颈替换实验”：保持其他模块不变，让人工参考方案或更强控制器暂时替代怀疑有问题的模块。看看它是否真的改善结果。

如果替代后依然无效，说明问题可能不在这一层，或者存在模块交互；可以进一步做两个模块的交叉替换，而不是盲目扩大训练。

### 2. 真实回放中的一个画面，不等于完整状态

真正影响后续行为的状态可能包括：朝向、攻击阶段、冷却、当前目标、队列、弹丸、增援、资源与生产进度，以及玩家此前已经获知的信息。

此外，还有 **AI 自身的状态**：当前计划、单位任务归属、历史记忆、循环网络的隐藏状态。

所以，“把单位、坐标和血量复制过去”往往不能复原原来的决策问题。

### 3. 反事实分叉必须满足两个额外条件

第一，给不同候选控制器提供相同、合法的观察历史，必要时进行记忆预热，而不是让一个看到完整上下文，另一个只看到单帧。

第二，分叉后必须有会响应的对手。

**不能更改己方打法之后，仍把人类原回放的后半段命令当成真实对手反应。** 对手原本的命令是针对原局面做出的；局面改变后继续机械执行，只能测对固定动作序列的效果。

可以使用冻结的反应式对手、多个对手模型，或者明确标注这是开环测试，但不能把它包装为完整反事实对局。

### 4. 没有快照分叉，也能开展有效实验

可采用经过验证的正常开局与脚本前缀，把游戏推进到目标局面；能够控制初始化时，比较重现的一致性。也可以直接进行整局模块替换和配对开局实验。

如果无法精确复原，就承认它是相近局面测试，不制造“精确反事实真值”。

另外，训练集与测试集应按**原始对局、场景家族、地图和对手来源**隔离。从同一场交战截出的许多相邻片段，不应被当作独立案例随机分到训练和测试中。

---

## 六、再选择方法：我的默认路线不是端到端 RL

我会让每种技术解决一个明确的瓶颈，而不是因为项目叫 AI，就尽早把整个游戏交给神经网络。

### 1. 第一阶段：参数化规则与小范围搜索

先建立可解释基线，再优化少量真正影响行为的参数，例如资源预留、集结条件、撤退条件、生产配比和任务优先级。

可以比较随机搜索、进化搜索或贝叶斯优化，但所有候选必须使用同一组训练对手与开发地图，并经过独立验收。

这一步不是为了证明 heuristic 足够，而是建立一个问题：

> 学习算法是否优于一个经过认真调优、但结构简单的控制器？

否则，RL 可能只是学会了几条本来就容易发现的阈值，却因为基线太弱而显得有效。

### 2. 第一个学习模块：给可执行方案打分

我的默认选择是：**先学习局部方案的结果预测或排序，而不是直接输出整个游戏的原始指令。**

例如，面对一次接战，先由可靠控制器提供“保持阵型交战”“撤回守备位置”“部分单位撤退”“等待增援”等可执行候选。小模型预测在给定目标和时间窗口内，各方案的结果及不确定性。

这里有一个必须守住的数据原则：

**只有实际执行过某方案的轨迹，不能凭空提供其他方案的效果标签。**

可以通过经过校验的分叉实验获得候选比较，通过专家提供带不确定性的相对判断，或者先只监督已执行方案的结果。不能把“这个局面最后赢了”直接解释成“当时的那个动作导致了获胜”。

随后检验模型是否真正改善决策：离线预测更准，但接入后没有改善，可能意味着预测目标不对、候选方案不对，或控制器无法实现预测时假设的行为。

### 3. 有可靠示范时，再做模仿学习与纠错

人类回放最有价值的内容不一定是每次点击，而可能是开局结构、部队任务、转型时机和关键决策。

但必须从合法观察构造输入，并区分成功执行的动作、无效输入和冗余操作。数据质量不足时，少量自录示范与人工纠错，也比大量失真的合成“专家数据”更值得作为起点。

模仿之后，让 bot 自己打，再对它实际遇到的困难局面补充指导。这个方向与 DAgger 的核心思路一致：训练数据需要覆盖学习者自身行为诱导出的状态分布，而不只是示范者走过的轨迹。([Proceedings of Machine Learning Research][5])

### 4. RL 的切入点：先优化一个有明确边界的决策层

我会优先考虑让 RL 选择宏动作或小队计划，例如生产方向、接战与撤退、守备力量分配，而把合法建造和可靠命令执行留给既有模块。

这样得到的是有持续时间的决策过程。一次“守住矿区”与一次“重新集结”可能持续不同长度，训练时应正确处理时间跨度，而不能假设每个宏动作只过去一个相同步长。

逐单位微操 RL 也可以研究，但应当在观察、命令语义、真实局面采样和基线全部可信后，单独验证其增益。

### 5. 奖励函数不能替代任务定义

“造成伤害”“保住单位”“多采矿”“少闲置”都可以成为诊断指标，但不应未经验证就相加为最终目标。

例如，只奖励保存坦克，可能鼓励放弃关键建筑；只奖励伤害，可能鼓励没有战略意义的换血；惩罚闲置，可能破坏合理的等待和埋伏。

主要目标应锚定真实胜负。需要稠密奖励时，可以研究势函数塑形：

$$
r'_t=r_t+\gamma\Phi(s_{t+1})-\Phi(s_t)
$$

这一形式在相应理论条件下具有策略不变性的依据，但实际实现仍需正确处理折扣、终止状态和可变时间步；它也不保证函数逼近与自博弈训练一定成功。([People at EECS][6])

**训练奖励可以帮助学习，正式验收不能只看训练奖励。**

### 6. 自博弈应建立在多样对手上，而不是只打自己

对手池应保留历史版本、不同倾向的脚本、已有外部 bot，以及专门寻找弱点的对手。不要让最新版本只和最新版本对战，然后把双方共同形成的习惯误认为通用能力。

AlphaStar 值得借鉴的重点，不是“使用了 RL”这件事，而是模仿学习起点、保留多样策略的训练体系，以及专门暴露弱点的对手。其公开说明也明确把这些机制作为方法的重要组成部分。([Google DeepMind][7])

但这不意味着要照搬 AlphaStar 的系统规模。对于这个项目，先复制**证据结构与训练组织方式**，比复制复杂网络架构更重要。

## 七、用一个具体实验说明：如何研究“残血坦克撤退”

假设基线经常出现坦克损失，研究 agent 提出：

> 固定血量阈值没有考虑守矿任务与增援，因此应训练一个上下文相关的撤退策略。

这只是待验证假设，不是已经找到原因。

### 第一步：确认是不是执行问题

选取真实失败片段，检查撤退指令是否生效，目的地是否可达，其他模块是否覆盖命令，重新发令是否改变了实际攻击与移动表现。

执行层没通过，暂停训练。

### 第二步：确认测试是否表达了正确任务

不要简单地摆一组坦克，然后十秒后按存活血量评分。

应保留任务上下文：后面是否有矿车与建筑，是否存在可守位置，敌人是否会追击，双方是否有增援，撤退的经济代价是什么。

“开阔地遭遇战”与“保护矿区”可以是不同测试家族，不能混成一个没有任务条件的标签集。

### 第三步：比较简单方案

比较始终交战、简单血量阈值撤退、经过人工检查的规则方案，以及学习方案。保持其他模块不变。

既看部队损失，也看守护目标、采矿中断、后续兵力和整局结果。诊断指标分别报告，不用一个漂亮的加权总分掩盖代价。

### 第四步：检验迁移与反例

测试不同地形、接敌方向、兵力组合和反应式对手，再接回完整 bot。

如果新策略保存了更多坦克，却让矿区被摧毁、整局胜率降低，结论不是“微操成功、战略以后再说”，而是：

> 在当前任务定义和系统组合下，这项改进尚不成立。

反过来，如果一种人类觉得激进的留场打法，在独立对局中稳定取得更好结果，也不应因为“不像撤退策略”而拒绝。

**这才是一个能迫使方法论进步的实验：它允许假设被否定，而不是无论结果如何都能宣布成功。**

## 八、正式评测必须同时防止噪声、过拟合和对手偏差

### 1. 用配对比较，而不是两组随意对局

候选与基线尽量使用相同地图、出生条件和对手版本，交换位置，记录完整配置。初始化随机性、策略随机性和训练随机性要分开管理。

这里的配对是为了减少无关变异，不是声称两条分叉轨迹中的所有随机事件都会保持一一对应。

### 2. 不只报告一个总胜率或 Elo

至少应能看到地图与对手分类表现、平局和超时、崩溃、关键失败类型，以及整体结果的不确定性。

总胜率可能掩盖某种打法上的严重退步。对手存在相互克制时，交叉对战矩阵也比单个排名更容易暴露问题。

胜率估计还需要足够样本。作为最简单的量级参考，独立胜负试验在胜率接近 50% 时，100 局的常用近似 95% 区间半宽约为 10 个百分点；大量同源、相关的局面不能直接套用这个估算。

深度 RL 评测研究也强调，仅比较少数训练运行的均值或中位数，容易得出与考虑统计不确定性之后不同的结论。([arXiv][8])

因此，“发现问题的小批量比赛”和“证明细小提升的比赛”需要不同规模。不能拿前者承担后者的结论。

### 3. 区分调参集、晋升集与最终保留集

开发集可以反复查看，晋升集用于固定流程比较候选，最终保留集不能在每次失败后都拿来调参。

一旦依据某个保留案例进行了修改，它就不再是同等意义上的未知测试，应当记录这一变化并补充新的保留案例。

场景生成器和评测器也要版本化。**若修改了评分规则，旧基线必须重跑，不能把新旧分数直接相减。**

### 4. 真人对局不能只留到项目最后

早期少量真人对局可以用于发现完全没覆盖到的打法，但不应据此做强胜率声明。

它的作用是打破当前对手池的共同盲点。后续需要更规范的真人验收时，再冻结版本、条件和取样方式。

## 九、如何重新组织 Codex：让它提出可证伪实验，而不是自建闭环自证成功

这里不应仅靠一句“请更严谨”，也不应把希望寄托在换个模型或多开几个 agent 上。

### 1. 给它的工作单位应是“研究假设”，不是“提高 AI”

不好的任务：

> 改进战术 AI，多生成一些场景测试，直到效果提高。

更好的任务是：

> 当前基线在一类真实守矿局面中失败。先区分观察、执行、交战评估与任务决策四种原因。为最可能的原因设计一个能否定它的实验。只修改一个指定模块，保留基线，并按冻结协议评测。提交原始结果与反例，而不是只提交结论。

每个实验至少应交代：观察到的现象、怀疑的机制、替代解释、干预方式、预期结果、否定条件和允许得出的结论范围。

**“没有改善，但排除了一个原因”应是合法交付。** 否则，开发流程会不断奖励把任何结果解释成成功。

### 2. 将提出方案、实现和裁决分开

研究 agent 可以提新方法，实现场景和代码；但正式评分协议、保留案例与晋升规则不能随同一次策略修改自由变化。

评测 runner 应生成不可随意改写的原始对局记录。修改评测需要单独审查，并重测基线。

这里的独立性主要来自**数据、权限、实现和证据来源**。几个使用相似假设的 agent 相互认可，并不构成独立验证。

### 3. 给它实际行为证据，而不只是控制台总分

每局应能追溯：

```text
当时允许观察到什么
→ 当前任务与资源约束是什么
→ 有哪些候选方案
→ 选择了哪个方案
→ 发送了什么指令
→ 后续实际发生了什么
```

记录的是事实、分数、状态和原因码，不需要冗长的事后叙述。

视频或回放用于看到阵型、卡位与任务上下文；结构化日志用于核对时间、对象和状态。两者应能对应到同一时刻。

自动分析可以帮助提出“疑似堵路”“目标频繁切换”等线索，但最终要回到可复现状态和引擎行为。

### 4. 把人类注意力留给新问题

让 agent 优先筛选新出现的失败类型、模型不确定性高的局面、多个控制器分歧大的局面，以及“局部指标提升但整局退步”的案例。

人类不必审核全部游戏，也不必替它设计所有策略。人类主要负责校验新任务、新场景家族和新的因果假设；已经明确的问题逐步进入自动检查。

## 十、我会按这些里程碑推进，而不是预先承诺一个训练日程

下面是我建议的默认路线。每个阶段都保留整局回归，不是等模型完成后才第一次验收。

| 阶段     | 主要产物                       | 进入下一阶段的依据              |
| ------ | -------------------------- | ---------------------- |
| 环境可信   | 锁定版本、合法观察适配器、机制测试、回放与吞吐量报告 | 能区分指令请求和实际效果，复现能力已明确   |
| 完整基线   | 能正常打完整局的简单 bot             | 主要失败不是崩溃、控制冲突或基础生产故障   |
| 评测可信   | 真实失败案例集、场景检查器、对照控制器        | 测试对被测能力敏感，已知错误能被发现     |
| 定位瓶颈   | 模块替换与反事实或配对实验              | 有证据表明某个决策瓶颈值得优化        |
| 首个学习模块 | 方案评估器、模仿策略或局部策略            | 优于认真调优的简单基线，并能改善独立整局结果 |
| 扩展训练   | 多样对手池、历史版本、逐步扩大任务范围        | 改进不只针对一种地图或一种对手        |
| 目标验收   | 冻结版本的保留集与真人测试              | 能在明确范围内给出有不确定性说明的能力结论  |

其中，RL 并不是必须在某一天开始的里程碑。它是通过前面这些检查之后，可以选择的一种优化工具。若参数搜索或监督学习已经能高效解决当前瓶颈，就没有必要为了路线“先进”而跳过它们；若规则结构成为上限，也应有证据驱动地替换，而不是永远固守规则。

---

## 最后的建议

你之前的经验最值得保留的，不是具体 heuristic 或训练代码，而是这个发现：**未经校验的合成环境，会让一个看似自动化的研究流程失去纠错能力。**

从零重建时，我会坚持三个原则：

**第一，真实引擎是行为事实的来源，但真实引擎中的人工场景不自动具有代表性。**

**第二，局部实验负责帮助理解，独立完整对局负责裁决改进；两者缺一不可。**

**第三，Codex 的职责应当是高效提出、实现和检验假设，而不是同时拥有定义问题、生成答案、制定分数和宣布成功的全部权力。**

因此，项目的第一项实质目标不是“训练一个小模型”，而是：

> **建立一个能够从失败回放出发，可靠回答“错在哪里、改了什么、为什么认为变好了、哪些情况下仍然不成立”的最小完整 AI 系统。**

一旦这个闭环可信，heuristic、搜索、模仿学习和 RL 才能真正累积进步，而不是累积无法判断价值的代码与实验。
