# 作战过程控制实验

2026-09-21，用户授权实施。玩家默认保持0.1.16；开发分支 `codex/operation-control`。本轮从已验证的新波次接口扩到主力的持续任务、改派、增援、重组、回防和撤回，沿用小模型、原生命令和既有战术/生产能力。

## 要回答的问题

当前模型只控制新一波装甲的时机、目标和初始投入。一个512局采样块中有189,929条记录，仅71,794条有多个动作可选（37.8%）；无兵和已有波次均会强制KEEP。这个测量证明控制范围受限，不证明它是学习不稳定的唯一原因。

拟比较旧权限与完整作战权限，两者接收相同新增任务事实，各自有BC起点与PPO；保持对手、奖励、执行战术和预算可比。主线与压力共同接入，继续保留各自步兵/经济承诺。旧launch-v1模型和稳定规则基线继续可运行。

源码核实的控制权接点：Bastion在原学习入口前会抽兵回防、按兵力损耗触发撤退、清目标；入口后又会自动增援。扩大范围需要把这些决策真正移交，不能在已运行的旧战略输出末尾覆盖一次任务。死亡、引用失效与到达等机械整理，与战略改派分开。

用户允许必要时咨询Pro，已在原项目会话完成具体控制权/状态/候选表示审查，并逐项核对本地接点。简报和状态在忽略目录 `work/consult-pro/operation-control/`。不以咨询代替本地验证。

## 当前实施证据

已抽取共用的全局/候选事实编码与按兵种比例选取成员，避免新旧接口各写一套事实逻辑。147项测试和类型检查通过。`runs/operation-facts-shadow` 中实时重构版和冻结 `f0e164a` 的同一BC模型比较3,623次决策，零差异，完整胜Supalosa于10,868 tick正常结束。这只验证共享编码抽取，没有声称扩大控制面已实现或更强。

新控制接口、控制权反例、两路线真实试运行、训练与对照结果将在实施后补记。当前尚未启动新的大规模服务器实验。

## 已实现的权限与表示

`operation-v2`保留实际`assault/joining/withdrawing`三组成任务事实，增加持续订单；没有另建独立推进的影子军队。模型每75 tick可KEEP，或原子地改令并补兵。订单含推进/搜索、集结、回防、撤回；当前目标加最多八个进攻目标、每类两个己方锚点，与0/1/三分之一/三分之二/全部的新增兵量组合，最多75个动作。保留伤亡后的主力身份、已抵达撤回点的成员和暂时不在观察中的己方单位；仅已确认的己方毁灭/失去所有权事件移除授权成员。事件过滤只认之前己方观察注册的引用，不读取攻击者或敌方事件。

KEEP不会重置订单年龄或兵力归属。三tick的事实整理只跟踪同一可见目标、确认己方损失、合并到达的增援，或在原主力全亡时提升幸存增援。模型订单中的两辆残存坦克不会被旧损耗阈值强制召回，新的基地受损也不能越权抢走主力。模型显式撤回后可中途改令；非推进订单清除旧夹击/增援目的及进攻生产上下文。新增援军先汇合现有主力，不因同时改目标就各自向敌基地行军。

共同输入为212维四时点事实/历史和48维动作描述；有无授权、订单类型与年龄、原始队伍存活/到达、当前目标清空、视野与兵力等均来自合法观察。连通性仅用于排除已知不可执行动作，一个受阻成员不否决其他可执行成员。不用旧风险评分屏蔽动作。

对照`scope=launch`也使用这些新事实和75tick战略节拍，但持续作战由抽取后的固定规则管理；记录固定规则的加兵、释放和改令，不把这些伪装为模型KEEP的效果。如v1一样，旧撤回者尚在途中时仍允许另开波次；窄权限只能命令新投入成员，旧撤回者继续由规则管理。v1另外保留作历史控制，战略节拍/输入已改变，不能称作原接口逐字复刻。完整权限暂不支持任意拆分、多目的并行、部分解散和征用独立矿区守备。

老师直接执行同一实际状态上的旧规则建议。部分召回、多目的与候选外成员组合，不能精确表达时记录-1及原因，BC排除这些动作标签；不做最近目标/最近兵数投影。老师模式本身允许执行这些候选外规则，因而必须报告覆盖率，不能宣称老师就是新动作空间内的可实现上限。

## 服务器预检与预定比较

首份端到端预检源码`16442e9`在独立tmux执行：四条路线（main/pressure × launch/operation）各有老师整局、BC/PPO、PyTorch→TF.js概率校验、冻结对手加载和最终小比较。模型为93,954参数；本机新接口同权重实时/冻结18,000次决策零差异，初始随机权重跑满上限。这证明加载/执行一致，不证明能力。随后修复了跨75tick节拍的目标清空通知保留，增加反例测试；当前157项Node测试及类型检查通过。

预检成功后正式批次的工作默认值：两种子47/83；每条路线128场老师；各自BC起点；两次PPO更新。每次先推进主线，再让压力应对冻结的新主线；同一轮内两权限/种子共享同一个对手池。固定四对手为0.1.16主线、0.1.16压力、旧阵地`b3a1f7c`及Supalosa，另外纳入对方路线两权限各自保留的一个学习对手。所有对手均被冻结；并列成绩保留旧候选，最新PPO与自己的BC仍在最终比较中同池重跑。

预计配置为5,824场直接采样/比较，加两块各512局的96/128并发校准，总计6,848场。这是有界配置，不是已完成局数或速度承诺。校准沿用已有工具，固定同一模型、地图、对手与策略随机数参数，用整块ticks/s和进程树内存选择并发；训练仍分别使用同等新增对局预算。模型、数据与回放仅存服务器私有目录，定位在忽略文件`work/server-feasibility/active-job.json`。地图均为已见开发图、出生不配对；用于检验控制范围是否更有用，不能宣称未见分布泛化或稳定竞技强度。

## 首轮学习起点与实际行为检查

八份BC（两路线×两权限×两种子）及跨运行时校验已完成。每份16局、固定四图四对手的开发初筛：主线launch47/83为11/9胜，operation47/83为8/9胜；压力launch47/83为13/9胜，operation47/83为9/8胜，零错误。只作冻结对手选择，不把一次16局或整体动作匹配率当作学习收益；最终将把每个PPO与自己的BC重新同池比较。

从主线operation83的Supalosa败局提取了具体检查点。52份原快照和终局一致，另用computer use查看15:00、16:00、17:20：11辆坦克确实进攻，依次摧毁3个碉堡、1座矿场和1辆矿车；四次建筑换目标都发生于前一目标清空之后。17:00可见6辆敌坦克回援，本方10辆平均43%血量仍KEEP；17:20剩4辆平均24%，有42个候选（含撤回）仍KEEP；18:20剩1辆才选择撤回。原规则建议在17:20同样KEEP，随后还有无法精确表示的部分召回/释放，说明这段需要学习超越老师的时机。

“首次模型出击”不能等同于“此前没出门”，因为未授权给模型的部队仍执行固定矿区屏卫/防守任务；“换目标次数”和“KEEP次数”也不直接表示乱改令或停止操作。本例不证明任何一次替代命令必能获胜，不将撤回后的无再次出击归因于大量闲置库存（当时剩余预备装甲很少）。精确定位与审查事实保存在忽略文件`work/operation-control/bc83-replay-review.json`；临时回放标签页和8643服务已关闭。

并发校准已完成：同模型/四图四对手各512局，96路为393.89秒、30,369.5 ticks/s、约85.5 GiB峰值树内存；128路为344.87秒、35,333.7 ticks/s、约110.0 GiB。实际选择128路。数据采样基于进程树测量，完整块含初始化和尾部；不是任意模型/对手的恒定速度。两份剩余BC及概率校验并行完成，用时201秒；参数、数据、种子和原始实验脚本未变，主编排在这些独立命令完成后继续。


分析器据此做了小幅修正：模型的推进命令按目标是否已清空区分改派，列出首次授权人数与首次撤回的既有成员/血量；规则教师和窄权限的固定规则管理单独说明。它解决“仅看5次推进就误读为反复取消目标”和“KEEP等于没有行动”的实际误读。上述录制局复算为清空后改派4、未清空改派0、首次授权11、首次撤回1，52份快照继续一致；没有加入新的胜负规则或策略阈值。


在最终结果产生前补定一项核查：如果开发选择实际保留的是较早PPO，且其精确模型SHA不在该路线的最终比较主体里，再用完全相同的冻结对手池和每格场次复验该检查点。主比较仍包含每个种子的BC和末次PPO，评分不变；补测至多四份各96局，重复SHA不重跑。这避免把“最后一次更新”自动当成最好的学习成果，定位`retained-check-status.json`。
