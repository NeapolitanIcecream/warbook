## 第一轮结果和修正

`688456b` 的 12 局小筛：候选 3/6 胜、2 负、1 上限；0.1.14 为 4/6 胜、2 负。同池为 Supalosa、0.1.14 pressure、0.1.8 bastion，城市/短图各一局。不能晋升。

城市 Supalosa 上限局 `runs/iteration-015-screen-1/mp29u2.map/supalosa/0-committed-015` 原回放 360/360 快照匹配。GUI 实看 40:00，大量坦克堆在基地。原因是新成员加入重置战术等待、清空目标区触发返家、探索命令没有稳定后续目标。第二轮修正这些衔接：少数掉队者自行追赶、清场后就地继续搜索，并使用静态路线提示。临时回放已关闭。

第二轮 `4d69196` 地图输入变更：只在第 0 tick 读取原始地形字段、初始桥面高度与中立建筑轮廓，构建独立 ngraph；不读战斗方单位、当前全图资源或实时引擎路径缓存。这是赛前地图先验的新信息条件，旧版整包对照包含信息条件差异，不称为纯策略消融。初始化被显式限制为第 0 tick。动态敌情、工程师目标仍来自合法可见 API。

第二轮还接入可见收入建筑捕获任务、攻守共用的坦克目标选择和友军后方伤员轮换。后两者需要真实对局验证，几何条件与命令提交不等于战斗收益。该冻结提交沿用了 dev.1 显示版本，实验按提交和内容哈希区分；后续候选递增显示版本。

第二轮城市/短图对 Supalosa、0.1.14 pressure、0.1.8 bastion：主线 6/6 胜，压制 5/6 胜，均正常结束。城市 Supalosa 主线局 13:37 胜、82/82 回放快照匹配；但碉堡挨打窗口只有两名 GI 有开火信号，不能因胜利就忽略防守配合问题。压制败局 35:58，432/432 匹配；坦克不足敌方时等待判断并非错误，早期压制没有获得足够收益才是需要调整的路线问题。

第三轮 `306f6e2` 让两个新路线对第二轮两路线与 Supalosa 交叉：主线 4/6 胜、1 负、1 上限；压制 2/6 胜、4 负。双方 Supalosa 均 2/2，压制仍未打过第二轮主线。城市主线败局的第三矿在 tick 10500 完成，当时己方仅六坦克、对方随后达到十辆；第三矿和护卫犬不应抢占恢复兵力的资金。短图上限局双方反复交战后资源不足，720/720 回放快照匹配，不同于第一轮大军完全停在家中的死等。

第四轮 `2c6de77` 收紧第三矿/额外护卫犬开支；恢复部队允许较小的成组增援。矿区响应点经过地形与已知建筑占位检查，近基地碉堡纳入步兵支援；正在前线开火的坦克不被普通矿区响应抢走。新增直接任务转换原因，避免后续预备队判断覆盖起因。

阶段结构检查：重复否决、集结计时重置与无效驻守点均有具体责任错误；分别在 Operations、StrikeTactics 和桥接地图提示中修复。保留现有战略/战术/生产三层，提取共用接战选择和独立静态图，不引入通用规划框架。尚不宣称有性能提升。

## 分析方法的具体改进

行军停滞原本把完整单位名单纳入连续区间标识，增援每次加入就抹掉之前的停滞证据。现在跟踪原有兵群的位置，允许新兵加入，不增加报告种类。在旧的 `screen-9/mp06t2.map/supalosa/0-contact-015` 上，简报现在直接定位 26:50–36:20：28 辆原有坦克采样位置在一格以内，期间仍发出 265 条移动命令。该改进用录制失败例验收，策略与胜负评分没有改变。
