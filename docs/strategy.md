# 首期战略规划：提前交付，以真实增益决定投入

状态：2026-09-15，**规划修订，未实施**。本文件替代此前口头提出的统一“6–8 周、100 局≥99%、3 地图/3 打法、胜率≥60%且提高≥10pp”安排。时间是基于当前预研的工作估计，指标是目标，不是已测结果或保证。

战略目标：尽早交付能打完整局的自有 RA2 AI，随后持续提高指定条件下的竞争力。**第 1–3 个工作日进入真实引擎，第 2 周形成自有完整玩家，第 4–6 周交付受限范围的可用版本；第 6–8 周用于验证、必要修复和有依据的能力扩展。** 不以启动 RL、完成平台或写完全部测试作为阶段成果。

## 1. 对原时间和指标的修订

| 原安排 | 问题 | 新安排 |
| --- | --- | --- |
| 第 1–2 周整体处理环境与稳定性 | 容易在第一次比赛前同时建设所有边界和工具 | 第 1–3 工作日先真实运行；基线与必要观察/记录随后一起完善 |
| 连续 100 局≥99%技术成功，作为早期验收 | 等待刷局会延迟反馈；容易混淆正常结束、超时和内部错误；观测比例也不证明真实可靠性≥99% | 首局有记录，小批量复跑定位故障；99%保留为交付版本的观测健康目标，不作为第一场或开始算法工作的门禁 |
| 到第 3–4 周才建立 3 地图/3 打法 | 来源数量可能不等于行为多样性，且反馈偏晚 | 第 2 周冻结一个能用的初始比较条件；逐步争取约 3 张地图、3 类实际不同打法，按行为和布局验证覆盖 |
| 胜率≥60%与相对基线≥10pp同时作硬门槛 | 未测基线和对手强弱，绝对值可能任意或冗余，也可能鼓励调整对手比例 | 主指标为固定目标分布上的整局得分增量，首期争取约 +10pp；取消统一60%门槛，始终报告外部对手上的绝对成绩 |
| 第 5–8 周引入搜索/学习 | 按日期选算法会造成无价值迁移 | 任何阶段按真实瓶颈选择规则、搜索、监督或 RL；有效规则可以构成最终首期版本 |

这里调整的是先后顺序、资源使用和声明方式，不降低观察合规、动作有效或评估可信的要求。工程 demo 与正式棋力结论使用不同级别的证据。

## 2. 时间口径与前提

- 以一位持续投入的主要负责人配合 Codex、每周约 5 个工作日估算；并行工作减少独立调查的等待，不假定多 agent 能线性压缩集成时间。
- 时间从开始实现计，不从写下本计划的日期计。首局估计要求游戏资源与可运行环境已可取得。资源、外部权限等等待单列并计入实际日历延期，不能靠重新命名 T0 隐藏延误。
- 现有源码审计、parser/mocked-method/模块加载探针可复用；它们尚未证明真实初始化、对局时序、终局识别或采样吞吐。
- 首期基准范围为一个国家、少量已核实地图、正常经济和完整胜负条件。工程试跑候选沿用 [前期决定](preimplementation-decisions.md)；正式信息、规则、地图与对手条件在运行后冻结。
- 首局不依赖 GPU、在线账号、真人大数据集、快照或分布式训练。后续计算资源按实测成本和预期收益规划；本轮不执行安装、探针、训练或游戏。

## 3. 累计里程碑

| 累计时间（基准估计） | 交付 | 验收重点 | 可以并行什么 |
| --- | --- | --- | --- |
| 第 1–3 工作日 | 第一次真实敌对对局与可查看记录；可先使用简单控制器/起始军队 | 实际动作、停止原因、defeat观察和录像可追踪；未确认正常结束就明确标记。这不是自有完整玩家交付 | 一人维护最小 driver，独立检查地图/对手实际接入 |
| 第 7–12 工作日，约第 2 周 | 自有最小完整玩家 B0 候选 | 能展开、采矿、生产、放置、补兵、寻找敌人并交战；明显的执行阻断已解决；少量重复完整局暴露失败。冻结比较基线和初始协议 | 从真实录像诊断一项高影响失败，维护小型对手池 |
| 第 3–4 周 | 可评估版本 v0.1 与首项有证据的改动 | 给出前后行为、完整局回归、失败与限制；正确性修复按正确性验证，竞争力声明才要求对应统计证据 | 只为一个值得比较的模块探索另一种方法 |
| 第 4–6 周 | 受限范围可交付版，通常以第 6 周为基准目标 | 简单运行入口、完整玩法、当前协议内的可靠行为；冻结候选做独立整局评估，报告下节指标及已知弱点 | 处理真实结构/性能问题，准备必要的最终样本 |
| 第 6–8 周，按证据使用 | 增益确认、稳定性修复或明确有价值的扩展 | 尽量达到约 +10pp 的主目标并有支持正增益的区间；确认适用范围、重要退化和未达项 | 已有结果足够时提前交付；缓冲期不自动加入新算法或功能 |

第 1 项与第 2 项必须分开：可以先让真实引擎运行，再逐步补全自己的玩家。首次运行不要求解决所有特殊可见性或建立严格自动胜负统计；开始积累正式棋力证据前，才必须验证本次比较实际涉及的信息和结果条件。

时间情景：顺利时约 **3–4 周**得到受限可用版；基准 **4–6 周**；基础兼容或行为问题较多时使用 **6–8 周**窗口。它们是条件估计，不是概率区间。第 3 工作日和第 2 周根据实际阻碍与运行成本重估；若第 8 周仍未达棋力目标，交付当前可运行产物、证据及新的范围/时间估计，不能把未达标重命名为成功。

## 4. 指标分三层

### 4.1 主指标：固定目标分布上的整局增益

正式比较前固定地图、对手版本与权重、国家/规则、信息与动作预算、结束和异常处理方式，定义 `D_target`。候选与基线 B0 均在该条件下评价：

`S(policy) = Σ weight(stratum) × mean(score within stratum)`

`Δ = S(candidate) − S(B0)`

正常胜/平/负可以记 1/0.5/0；bot/runner错误、超时、未决结束与可重跑的外部故障按预先写明的协议处理，分别报告数量。默认将 bot 自身故障计为该方失败；可归因外部基础设施的故障按固定规则排除或重跑并单列；超时不自动视为平局。分母、排除和重跑不能随候选表现改变。不能把 `isFinished()` 或资产优势直接当作胜利。

**首期改进目标为 Δ 点估计约 +10 个百分点；在本计划的统计验收中，只有预定的 95% 区间下界高于 0，才称“正向增益已确认”，否则报告观察差异与不确定性。** 点估计 +10pp 且区间下界>0，支持“存在提升”，不等于证明“真实提升至少10pp”。第 2 周可依据未冻结前的 B0 水平、实际方差与预算校准最小有价值增量，并记录理由；冻结后的变化作为新目标版本，不用旧结果追认达标。

B0 在基础玩法贯通、明显执行错误修复并经过一次合理简单调优后冻结，避免故意选弱基线。固定原始 B0 用于累计进步，同时保留当前最好版本作增量对照；正确性修复无需每次等待相对原始 B0 的大型比赛。

取消统一60%门槛，但**保留绝对水平报告**：固定外部对手锚点、各地图/打法成绩、对当前最好版本的变化，以及严重弱点。若只相对弱 B0 提升却仍经常被外部锚点击败，应明确称为进步中的研究版。外部 bot 也不是高手水平的天然标尺。

### 4.2 可用性：尽早运行，后期累计可靠性证据

| 指标 | 目标与使用方式 |
| --- | --- |
| 启动记录闭合 | 每次正式启动均关联结果、错误、截断或未决状态；不静默丢局。这是记录正确性要求 |
| 完整玩法 | 自有基线能重复完成正常经济/生产/交战链，当前阻断性缺陷得到修复；用相关回放和复跑验收 |
| 技术健康 | 交付版本争取最近100次目标条件下的启动中，bot/runner内部故障≤1次；不足100次时只报告实际计数，不宣称该窗口目标达成 |
| 截断与未决 | 与内部错误分别列出，不能因runner成功按上限退出就算正常完成。反复无法完成对局的版本不称为可用 |
| 信息与执行 | 本次正式比较使用的观察路径、动作链与结果判定有对应检查；已知会改变结论的问题先修正 |

100局只是可用性观察窗口，可复用冻结版本的正常评估局，不是算法启动门槛。即使100局零故障，也不构成“真实成功率已被证明≥99%”；应报告样本条件与不确定性。少量真实复跑更适合早期发现问题，不能先刷容易完成的局来优化比例。

结束证据采用能支持本次规则的最小可验证路径；比赛结果证据与运行器是否无故障分开记录。无需在比较普通对局前统一全部终局形态，但确实缺少依据的记录应标未决，并按固定协议处理。

### 4.3 诊断与效率：用于选工作，不代替棋力

- 争取至少约3张具有实际布局差异的地图、3类关键反应不同的对手；最初可以更少。覆盖依据是实际行为/布局，不是仓库名、难度标签或文件数量。
- 尽早分配开发与留出来源；建议初始约2张开发图、1张留出图，并保留未参与调参的对手/设置。只有一张留出图时，结论限于该设置，不宣称广泛跨地图泛化。条件不足时明确未验证维度。
- 保留经济停滞、分批接敌、任务冲突、无效/过期命令、关键目标损失等诊断，按对当前胜负的影响排优先级，不优化任意加权过程分。
- 第一次运行后测端到端完整局成本、必要决策延迟和有效采样吞吐。**进入稳定迭代后，小批量结果争取当天返回**，作为反馈速度的工作目标；具体局数与资源由实测决定，不承诺某个 GPU 或 tick/s。

## 5. 实验预算与候选晋升

采用“便宜诊断 → 有限筛选 → 少数候选独立确认”的结构，避免每次小修改都跑最终规模。

| 层次 | 规划参考 | 决定什么 |
| --- | --- | --- |
| 机制/正确性 | 一至数段相关行为，必要时少量完整局回归 | 修复是否生效，接口或解释是否错误 |
| 开发筛选 | 每候选约20–40局起步，按实际成本调整 | 是否有值得继续检验的信号；小幅差异不能据此宣布胜率提高 |
| 里程碑确认 | 冻结少数候选及协议，独立评价；预算同时包含重测 B0 | 是否达到指定范围内的竞争力声明 |

[既有统计分析](statistical-budget.md) 给出的量级是：独立二元结果、50%对60%、双侧5%检验、80% power 的正态近似约需 **388局/版本，合计776局**；5pp差异约需3130局。这些不是实际比赛预算定论，也不适用于直接对战、相关来源、平局或多次训练的所有设计。它解释了为什么首期优先追求有实际价值的较大增益，并只给少数候选昂贵确认。

第2周用实测吞吐、实际结束类别和初步方差决定正式预算及查看节点。总成本包括候选筛选、基线重测、确认、故障诊断以及必要训练重复，不能只算最好模型的一次训练。若成本不合适，先减少并行候选、聚焦更大问题、优化已测瓶颈或调整时间；不能删除失败或缩小分母来保持原声明。

晋升集可反复帮助工程选择，但不是永远未知。最终候选冻结后使用未参与该选择的样本；如果看结果后继续修改，该证据归入开发资产。一个固定模型打很多场不证明训练方法稳定；声称某学习方法可靠优于替代方案时，另考虑独立训练重复。

## 6. 工作组织与投入决策

只保留一条主控制/集成线；可并行维护最小运行与证据、独立诊断一个真实失败。已有接口足以支持下一场比赛时立即运行，不把观察全覆盖、强外部对手、seed/fork、异步服务或 RL 平台一起放入关键路径。

| 当前证据 | 优先投入 | 改线条件 |
| --- | --- | --- |
| 基础玩法不完整或命令不生效 | 最小规则与执行修复 | 能真实执行后再研究选择算法 |
| 有清楚的少量参数或规则问题 | 参数优化、简单对照 | 两轮无行为变化也没排除解释时换原因 |
| 有好候选、预测可信且延迟允许 | 有预算的搜索/规划 | 模拟得分高而实际无益，先查模型与目标 |
| 合法输入对应可靠示范或结果标签 | 排序/预测监督学习、必要纠错 | 离线好而闭环差，先查分布、候选和执行 |
| 确有连续闭环决策空间、反馈可信、样本预算足够 | 局部 RL 判别实验 | 只增奖励、只赢旧版或成本明显不合算时缩小任务或回到最好简单方案 |

RL 可早试，也可不进入首期。对手池维护和数据加工只服务正在研究的问题；没有真实失败时，不并行生成大量想象中的微操任务。每周交付当前可运行版本及本周证据，允许有价值的阴性结论，不承诺每周必然涨胜率。

## 7. 重构、性能与缓冲

沿用用户偏好：默认每3轮实质迭代或里程碑结束时简短检查，重复故障、耦合修改、控制权混乱或性能瓶颈提前触发。没有具体问题直接继续，不强制重构、不新增审批或报告。

确有需要就暂停受影响的新功能，先做改善。结构依据可以是修改成本、职责冲突或无法隔离实验，不必等待性能 benchmark；性能改动则针对同样负载、行为和决策预算比较。常规改善尽量在约1–3工作日内恢复一个可运行增量，较大问题拆分交付；这个范围是控制投入的估计，不是让必要修复到点未完就放弃。

第4–6周的交付估计已包含正常的修复、重构与测量；第7–8周是为已出现的兼容、关键行为或验证成本保留的弹性，不强制分配固定比例给基础设施。问题解除即恢复主线。若性能瓶颈并不限制当前实验或部署预算，不为更漂亮的基准数字提前改架构。

## 8. 复盘点与失败替代路线

| 时点/触发 | 检查与决定 |
| --- | --- |
| 首3工作日 | 资源能否初始化、首场行为是否出现？资源缺失明确记外部阻塞；外部 bot 未通则先用自有简单控制器，不回到无限源码预研 |
| 第2周 | 冻结 B0 与初始目标；核实涉及的信息/结果条件；用实际样本成本校准第4–6周交付范围与 +10pp 目标的预算意义 |
| 两轮无有效进展 | 区分观察、执行、目标、候选、介入时机或模块交互；换一个能区分解释的实验，不继续同类阈值微调 |
| 局部好、整局差 | 暂停扩大训练，检查任务代价和接口；不将局部成绩当成功交付 |
| 第4周 | 展示可评估版本。若基础链仍不可靠，优先修复并缩小下一阶段扩展，而非启动更大模型或平台 |
| 第6周 | 有足够证据则交付；有明确缺口则用缓冲做针对性修复/确认，不自动扩充项目 |
| 第8周 | 对照原目标报告已达与未达、关键证据和下一阶段估计；不凭时间消耗或完成文档宣称 AI 达标 |

计划中的缩小范围必须显式记录：少地图、少国家可以支持一个受限版本；工程观察条件不能冒充公平协议；默认结束信号不能冒充赢家；已见样本不能冒充留出。真实运行证据不足时降低的是声明范围，而不是记录真实性。

## 9. 本轮规划的边界

本次仅写规划和文档关联，没有安装依赖、运行探针/游戏、修改 bot 或启动训练。执行细节沿用 [实施路线](roadmap.md)、[接口契约](interface-contract.md)、[评估协议](evaluation.md) 和 [实验菜单](first-experiments.md)；时间与主指标以本修订为准，实测数据出现后按上述复盘点更新。
