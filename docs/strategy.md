# Agent 全权研发战略：按实际耗时滚动预测，持续交付可玩版本

状态：2026-09-15，**规划修订，未启动研发**。用户已明确新的分工：Codex Agent 全权负责自动化研发，用户仅作为用户/玩家检验体验和结果。此前基于“一位主要负责人配合 Codex”的工作周估计已撤回；不能把它除以假定加速倍数，改称 Agent 的交付时间。

战略目标：尽快交付用户能亲自对战的 RA2 AI，并持续提高指定条件下的竞争力。**首个6–12小时是立即推进真实运行的校准窗口；随后滚动给出未来24小时和72小时的产物预测。** 下文的小时数是尚未校准的阶段目标/检查预算，不是已测开发速度，也不承诺在72小时达到高手水平或 +10pp 增益。

## 1. 责任与原计划的变化

Agent 负责技术优先级、方案、实现、集成、实验设计、对手与数据、排错、重构、性能优化、版本晋升、运行维护和证据报告。用户不需要选算法、审核实验、调参数、查日志或管理任务；用户只需使用/对战并表达体验。Agent 将这些反馈转成可复验的问题并自主安排改进。

原来的指标修订继续保留：100局≥99%不是早期门禁；取消统一60%胜率门槛；约 +10pp 是固定目标分布上的改进目标，正式确认需要独立证据。新增变化是**排期、研发责任和可玩交付定义**。

| 原安排 | 新安排 |
| --- | --- |
| 人类工作日/工作周预测，4–6周或6–8周交付 | 撤回固定周数，以墙钟耗时、关键依赖、实际吞吐和修复周期滚动预测 |
| 用户可能参与技术判断与场景审查 | 技术与实验裁决由 Agent 负责；用户提供普通玩家反馈即可 |
| 完整 headless 对局及录像即可作为主要交付 | 分开研发基线、可观看证据与真正可对战入口；玩家交付需验证打开、加入、操作、结束和再次开局 |
| 以周为单位回顾进展 | 首轮6–12小时校准，之后约24小时或关键事件重估；这只是执行计划，不是本轮创建的定时任务 |
| 常规重构按1–3个人类工作日估计 | 在具体阻碍上做可运行增量，根据真实工作量给小时范围；完成必要改善就恢复主线 |

自主研发不降低结果可信度，也不把模型、token、提交数或文件数量作为进度。成功由可玩行为、实际问题的解决和独立对局增益支持。

## 2. 时间模型与执行条件

用户关心的主时间是**从实际启动到交付的日历耗时**，包含排队、额度等待、机器睡眠、中断和外部资源等待。不能用“Agent实际只工作了几小时”掩盖用户已等了几天，也不能重置起点来隐藏延期。

| 时间/成本 | 如何使用 |
| --- | --- |
| 日历耗时 | 面向用户的交付时间，保留启动时刻与上次预测 |
| 关键路径执行时间 | 必须先后完成的实现、集成、仿真、修复和确认；决定下一项交付 |
| 并行任务投入 | 各 worker 工作量之和，用于解释资源成本；不能相加成日历时间，也不代表进步 |
| 等待 | 标记是否阻塞关键路径；与并行工作重叠的等待不重复累加 |

预计剩余时间按工作依赖中的最长路径估算。已测完整流水线的有效采样率记为 `R`，一个固定批次约需 `N/R` 的采样时间，再加未被该测量覆盖且不能重叠的实现/训练/审阅时间。R 的分母要包含该流水线实际发生的启动、记录和失败重跑开销，不能只拿空引擎 tick/s 计算交付速度。

例：若实际流水线达到每小时100个可用完整对局，776局仅采样约需7.8小时；每小时20局则约38.8小时。**这是条件算例，不是当前实测吞吐，也不包含发现有效新策略所需的未知轮次。** 代码生成可能更快，但串行因果试验、计算吞吐和必要返工仍需要真实时间。

首轮6–12小时直接推进游戏资源初始化、真实行动与试玩入口核查，沿途从现有日志记录单局成本、并发效果、失败和修复耗时；不另建计时平台。未跑通时只报告具体阻碍和下一条解法，不编造吞吐或长期 ETA。

执行前提是可用游戏资源、工具/账户访问、足够的既有使用额度与可保持运行的主机/执行环境。缺少不可替代的资源或平台身份授权时，Agent 一次说明具体所需输入；已知和已授权内容直接复用。常规研发、试验和修复不反复交由用户批准，额外资源投入仍遵守已有范围。

自动决策与持续运行条件是两个问题。官方 [Long-running work](https://learn.chatgpt.com/docs/long-running-work) 说明了 `/goal`、完成标准、同任务内继续工作以及本地工作区/主机保持可用等条件；长任务沿用既有访问边界。这不证明当前任务已经启用长时间执行、续接或后台调度。真正启动时使用现成的长任务/续接机制并检查其可用性，不先建设通用 Agent 平台；**本轮没有创建 goal、自动化任务或后台研发进程。**

## 3. 首轮自主阶段与滚动预测

以下从实际启动计为累计墙钟检查点，假设资源和持续执行条件可用。它们表达希望投入到哪个结果的预算，不是新的无依据工期承诺；外部等待仍计入实际日历报告。

检查窗口不要求把时间用满。提前跑通、取得足够校准数据或完成可玩版本时，立即交付并推进下一项；不等待固定时间点，也不把一次短对话冒充持续运行了数小时。

| 检查窗口 | 优先争取的结果 | Agent 在边界应作出的决定 |
| --- | --- | --- |
| 6–12小时 | 第一次真实敌对运行、实际动作与停止记录、可查看回放；明确玩家体验入口及外部依赖。可先使用朴素控制器，不冒充自有完整 AI | 用真实运行问题校准下一段；若尚未初始化，不扩大策略、学习或研究设施，继续解决最小阻碍 |
| 约24小时 | 自有玩家的基本完整链：展开、经济、生产、放置、补兵、寻找敌人、交战；保存最高完成度可运行版本和实际失败 | 给未来24小时的具体产物与时间范围，及未来72小时的条件预测；B0/协议具备条件时冻结，否则标明缺口 |
| 约72小时 | 争取交付用户可亲自对战的受限版本，并有完整记录和一轮真实改进闭环 | 已可玩就交付体验；未可玩就明确缺口，不拿回放替代。按证据决定下一段做可靠性、战术、范围扩展还是性能 |
| 之后每约24小时或主要里程碑 | 更新可运行/可玩版本、当前证据、未来24/72小时预测 | 不承诺每个窗口必然涨胜率；检查点不自动停止研发或要求用户接手技术工作 |

预测写三件事即可：**交付什么、预计时间范围、主要依赖/不确定项**。第一次24/72小时预测在首轮实测后给出；在没有可比较候选时，可预测完成下一轮判别实验，不能可靠预测何时获得10pp提升。关键阻碍变化、吞吐/修复耗时明显超预期、连续两轮无有效进展时提前重估；保留上次预测和偏差原因。

### 玩家通路前置

最短已知候选是外部 Node Bot 对接官方浏览器客户端的在线对局，API要求 `apiKey`、`xwolApiUrl`、`clientUrl`，并可通过 `onGameCreate` 提供加入链接。账户可用不等于拥有 Bot API 凭证；实际加入、实时操作和兼容性还未验证，见 [环境审计](environment-audit.md)。

Agent 负责准备并维护用户入口、启动后台进程、配置和重新开局，用户无需为试玩运行终端或修环境。若缺凭证，Agent 先查清可用路径与平台所需授权，并继续 headless 玩家和自动实验；不会把全部研发停在等待上。浏览器内集成 bot 或自建兼容服务尚未证明是廉价备选，只在实际可行性明确后采用，不默认大改引擎。

玩家交付的最低链路为：**打开入口 → 加入对局 → 实时操作并与 AI 交战 → 结束/退出 → 能再次开局**。headless 是研发基线，回放是证据；只有上述链路实际通过，才能标为“用户可玩”。工程试玩中 `api-shroud-v0` 的信息限制简短披露，不因用户愿意试玩就获得公平竞技认证。

在线试玩还需验证真实时序和断线/重开；不能用暂停离线模拟等待推理的行为宣称满足在线实时条件。首版可以采用同步规则与受限功能，先保持玩家能完整体验。

维护固定的可玩版本与实验候选；失败试验不破坏用户入口。每次交付附版本、简短变化、已知弱点和希望观察的一两个体验问题。用户不试玩/不回复时继续自动对局、排错和有价值改进，不把未反馈当认可；用户开始玩时优先保证体验，按需要降低同机实验并发。

## 4. 指标分三层

### 4.1 主指标：固定目标分布上的整局增益

正式比较前固定地图、对手版本与权重、国家/规则、信息与动作预算、结束和异常处理方式，定义 `D_target`。候选与基线 B0 均在该条件下评价：

`S(policy) = Σ weight(stratum) × mean(score within stratum)`

`Δ = S(candidate) − S(B0)`

正常胜/平/负可以记 1/0.5/0；bot/runner错误、超时、未决结束与可重跑的外部故障按预先写明的协议处理，分别报告数量。默认将 bot 自身故障计为该方失败；可归因外部基础设施的故障按固定规则排除或重跑并单列；超时不自动视为平局。分母、排除和重跑不能随候选表现改变。不能把 `isFinished()` 或资产优势直接当作胜利。

**首期改进目标为 Δ 点估计约 +10 个百分点；在本计划的统计验收中，只有预定的 95% 区间下界高于 0，才称“正向增益已确认”，否则报告观察差异与不确定性。** 点估计 +10pp 且区间下界>0，支持“存在提升”，不等于证明“真实提升至少10pp”。取得可用 B0 和首批真实成本数据后，可在正式冻结前校准最小有价值增量并记录理由；冻结后的变化作为新目标版本，不用旧结果追认达标。24/72小时检查点未达到预期，不自动降低此目标。

B0 在基础玩法贯通、明显执行错误修复并经过一次合理简单调优后冻结，避免故意选弱基线。固定原始 B0 用于累计进步，同时保留当前最好版本作增量对照；正确性修复无需每次等待相对原始 B0 的大型比赛。

取消统一60%门槛，但**保留绝对水平报告**：固定外部对手锚点、各地图/打法成绩、对当前最好版本的变化，以及严重弱点。若只相对弱 B0 提升却仍经常被外部锚点击败，应明确称为进步中的研究版。外部 bot 也不是高手水平的天然标尺。

### 4.2 可用性：尽早运行，后期累计可靠性证据

| 指标 | 目标与使用方式 |
| --- | --- |
| 启动记录闭合 | 每次正式启动均关联结果、错误、截断或未决状态；不静默丢局。这是记录正确性要求 |
| 完整玩法 | 自有基线能重复完成正常经济/生产/交战链，当前阻断性缺陷得到修复；用相关回放和复跑验收 |
| 玩家可用性 | 用户能打开入口、加入、实时操作、结束并再次开局；Agent自行预检并维护入口，用户仅评价体验 |
| 技术健康 | 交付版本争取最近100次目标条件下的启动中，bot/runner内部故障≤1次；不足100次时只报告实际计数，不宣称该窗口目标达成 |
| 截断与未决 | 与内部错误分别列出，不能因runner成功按上限退出就算正常完成。反复无法完成对局的版本不称为可用 |
| 信息与执行 | 本次正式比较使用的观察路径、动作链与结果判定有对应检查；已知会改变结论的问题先修正 |

100局只是可用性观察窗口，可复用冻结版本的正常评估局，不是算法启动门槛。即使100局零故障，也不构成“真实成功率已被证明≥99%”；应报告样本条件与不确定性。少量真实复跑更适合早期发现问题，不能先刷容易完成的局来优化比例。

结束证据采用能支持本次规则的最小可验证路径；比赛结果证据与运行器是否无故障分开记录。无需在比较普通对局前统一全部终局形态，但确实缺少依据的记录应标未决，并按固定协议处理。

### 4.3 诊断与效率：用于选工作，不代替棋力

- 争取至少约3张具有实际布局差异的地图、3类关键反应不同的对手；最初可以更少。覆盖依据是实际行为/布局，不是仓库名、难度标签或文件数量。
- 尽早分配开发与留出来源；建议初始约2张开发图、1张留出图，并保留未参与调参的对手/设置。只有一张留出图时，结论限于该设置，不宣称广泛跨地图泛化。条件不足时明确未验证维度。
- 保留经济停滞、分批接敌、任务冲突、无效/过期命令、关键目标损失等诊断，按对当前胜负的影响排优先级，不优化任意加权过程分。
- 第一次运行后测端到端完整局成本、必要决策延迟和有效采样吞吐。记录从一个具体假设到下一步可作出决定的实验周转时间，并优先缩短真正阻塞迭代的环节；token、代码量、提交量和总局数仅作成本/过程记录，不代替进步。

## 5. 实验预算与候选晋升

采用“便宜诊断 → 有限筛选 → 少数候选独立确认”的结构，避免每次小修改都跑最终规模。

| 层次 | 规划参考 | 决定什么 |
| --- | --- | --- |
| 机制/正确性 | 一至数段相关行为，必要时少量完整局回归 | 修复是否生效，接口或解释是否错误 |
| 开发筛选 | 每候选约20–40局起步，按实际成本调整 | 是否有值得继续检验的信号；小幅差异不能据此宣布胜率提高 |
| 里程碑确认 | 冻结少数候选及协议，独立评价；预算同时包含重测 B0 | 是否达到指定范围内的竞争力声明 |

[既有统计分析](statistical-budget.md) 给出的量级是：独立二元结果、50%对60%、双侧5%检验、80% power 的正态近似约需 **388局/版本，合计776局**；5pp差异约需3130局。这些不是实际比赛预算定论，也不适用于直接对战、相关来源、平局或多次训练的所有设计。它解释了为什么首期优先追求有实际价值的较大增益，并只给少数候选昂贵确认。

在 B0 可用且首批运行完成后，用实测吞吐、实际结束类别和初步方差决定正式预算及查看节点。总成本包括候选筛选、基线重测、确认、故障诊断以及必要训练重复，不能只算最好模型的一次训练。若成本不合适，先减少并行候选、聚焦更大问题、优化已测瓶颈或调整时间；不能删除失败或缩小分母来保持原声明。

晋升集可反复帮助工程选择，但不是永远未知。最终候选冻结后使用未参与该选择的样本；如果看结果后继续修改，该证据归入开发资产。一个固定模型打很多场不证明训练方法稳定；声称某学习方法可靠优于替代方案时，另考虑独立训练重复。

## 6. 工作组织与投入决策

root Agent 负责唯一的主控制/集成线及最终技术决策；可委派独立证据工作和一个有边界的探索任务。已有接口足以支持下一场比赛时立即运行，不把观察全覆盖、强外部对手、seed/fork、异步服务或 RL 平台一起放入关键路径。正式评测协议与候选修改分开，独立性来自记录、固定条件和反例，不能只靠多个 Agent 赞同。

| 当前证据 | 优先投入 | 改线条件 |
| --- | --- | --- |
| 基础玩法不完整或命令不生效 | 最小规则与执行修复 | 能真实执行后再研究选择算法 |
| 有清楚的少量参数或规则问题 | 参数优化、简单对照 | 两轮无行为变化也没排除解释时换原因 |
| 有好候选、预测可信且延迟允许 | 有预算的搜索/规划 | 模拟得分高而实际无益，先查模型与目标 |
| 合法输入对应可靠示范或结果标签 | 排序/预测监督学习、必要纠错 | 离线好而闭环差，先查分布、候选和执行 |
| 确有连续闭环决策空间、反馈可信、样本预算足够 | 局部 RL 判别实验 | 只增奖励、只赢旧版或成本明显不合算时缩小任务或回到最好简单方案 |

RL 可早试，也可不进入首期。对手池维护和数据加工只服务正在研究的问题；没有真实失败时，不并行生成大量想象中的微操任务。每个主要运行窗口交代当前可玩/可运行版本、已经验证的变化和下一段自主工作，允许改变下一步决定的阴性结论。用户的“不会防守”“太卡”“没挑战”等反馈由 Agent 关联对局版本和记录、定位原因并复验，不要求用户设计实验或精确标注日志。

用仓库内已有状态记录保留当前可玩版本、候选、冻结基线、主要发现、下一步和仍在运行的进程/产物位置；在上下文切换或续接时恢复，不重复做已完成工作。保持记录简短，不新建调度平台。用户反馈属于开发证据，不自动等于总体胜率或最终未见测试。

## 7. 重构、性能与缓冲

沿用用户偏好：默认每3轮实质迭代或里程碑结束时简短检查，重复故障、耦合修改、控制权混乱或性能瓶颈提前触发。没有具体问题直接继续，不强制重构、不新增审批或报告。

确有需要就暂停受影响的新功能，先做改善。结构依据可以是修改成本、职责冲突或无法隔离实验，不必等待性能 benchmark；性能改动则针对同样负载、行为和决策预算比较。Agent 根据具体问题估计下一个可运行改进的耗时，较大问题分步替换，不沿用人类工作日额度，也不另等用户确认。

滚动 ETA 包含必要修复、重构、测量和集成；不强制分配固定比例给基础设施。若预计修复会占据整个下一运行窗口，说明它解除的当前阻碍及更小替代方案，做出继续或拆分决定。问题解除即恢复主线。若性能瓶颈并不限制当前实验或玩家体验，不为更漂亮的基准数字提前改架构。

## 8. 复盘点与失败替代路线

| 时点/触发 | 检查与决定 |
| --- | --- |
| 首个6–12小时窗口 | 资源能否初始化、首场行为是否出现、玩家入口是否有可行路径？缺失输入精确列出；外部 bot 未通则先用简单控制器，继续可推进部分 |
| 约24小时 / B0可用时 | 核实涉及的信息与结果条件，冻结 B0 和初始目标；按真实工作量给未来24/72小时预测和资源需要 |
| 两轮无有效进展 | 区分观察、执行、目标、候选、介入时机或模块交互；换一个能区分解释的实验，不继续同类阈值微调 |
| 局部好、整局差 | 暂停扩大训练，检查任务代价和接口；不将局部成绩当成功交付 |
| 约72小时 | 检查真正可玩链路和完整玩家；未达时报告实际完成物与准确缺口。下段投入由瓶颈决定，不把检查点当验收成功或自动停止 |
| 主要里程碑 / 约24小时滚动更新 | 保留上次预测，解释偏差；给下一段具体产物及区间。没有有效进展则调整机制，不反复延长同一计划 |
| 使用额度、主机或权限改变 | 更新关键路径与实际日历预测，保留可恢复状态；独立可推进的工作继续，不伪装为一直满负荷运行 |
| 玩家反馈或准备交付 | Agent核对版本、入口和行为变化，吸收反馈；反馈缺席不算认可，也不阻塞独立的自动研发 |

计划中的缩小范围必须显式记录：少地图、少国家可以支持一个受限版本；工程观察条件不能冒充公平协议；默认结束信号不能冒充赢家；已见样本不能冒充留出。真实运行证据不足时降低的是声明范围，而不是记录真实性。
