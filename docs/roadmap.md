## 阶段与进展依据

| 阶段 | 交付 | 能支持的结论 | 下一步 |
| --- | --- | --- | --- |
| 最小完整运行 | 固定版本、正常对局、动作效果、终局和 replay | 当前环境能运行并解释行为 | 建立基线与研究失败 |
| 玩家可对战入口 | Agent维护的加入、实时操作、结束和重开链路 | 用户可亲自体验；单独的回放不满足这一交付 | 接收普通玩家反馈，Agent转成研究问题 |
| 可信观察和基线 | 已定义的信息条件、泄漏检查、模块化玩家 | 该条件下的行为与失败可追踪 | 对照检查与失败分类 |
| 可信评估 | 小规模真实案例、针对性故障注入、保留对局 | 能辨别声称测量的缺陷 | 比较瓶颈解释 |
| 首项改进 | 模块干预、简单替代方案、独立整局结果 | 指定条件下的改善或原因排除 | 保留、切换或扩大证据 |
| 学习与扩展 | 按需学习模块、更多地图/国家/对手 | 改进是否迁移且保留旧能力 | 扩大任务范围 |
| 目标验收 | 冻结候选与条件、保留对局，必要时真人评估 | 带不确定性与范围说明的实力结论 | 报告能力与剩余缺口 |

这些阶段可适度重叠。观察问题可在首次引擎运行中调查；完整回归贯穿后续开发。RL 与快照分叉均不是必经里程碑。

各阶段采用同一开发节奏：默认每 3 轮实质开发/实验迭代或里程碑结束时，简短检查代码结构和性能；反复故障、耦合修改或采样瓶颈会提前触发。检查发现确有改善需求时，暂停相关新功能，完成有范围的重构/优化与适当验证后继续；没有问题就直接推进，不强制重构，也不新增审批或报告流程。详见 [方法论中的开发平衡约定](methodology.md#开发速度结构与性能的平衡)。

## 首轮实施：一条可观看、可解释的正常整局

### 1. 确定最小环境

- [ ] 记录准备采用的 API/引擎版本、运行时、地图与规则来源及哈希。
- [ ] 确认本地游戏资源路径；资源不入库。
- [ ] 选一个国家、少量地图与明确的正常开局选项，标明哪些用于开发、哪些保留。
- [ ] 写明信息和操作条件；暂不以“与人类完全等价”描述未验证的接口。
- [ ] 基于官方示例安装必要依赖并生成锁文件，建立启动/结束/清理链路。
- [ ] 同时核查用户对战通路：在线外部Bot所需的服务凭证/端点和加入URL；由Agent准备入口、维护进程并验证玩家可操作和重开。缺少不可替代权限时一次说明，headless研发继续。

当前设计基准为 API 0.79.0；如果实施时更换版本，先复核相关接口和行为。[前期分析收束](preimplementation-decisions.md) 已选 Americans 镜像、`mp03t4.map` 及官方示例选项为首场工程候选；尚未验证地图实际可用性和公平性。资源路径、正式地图/对手分布、操作预算与资源上限仍由实施验证确定。分析 parser 的依赖锁文件仅用于探针，不能当作 bot 项目已经安装完成。

### 2. 形成最小行为与日志

- [ ] 创建能展开、生产、组织一次行动并完成终局的简单 bot。
- [ ] 将角色观察与裁判真值分开；策略入口通过显式观察适配器。
- [ ] 对一个生产动作和一个移动/攻击动作检查请求、发送及后续状态。
- [ ] 记录任务归属和命令仲裁，辨认“无新指令”时引擎仍在做什么。
- [ ] 对正常结束、超时、bot 错误、引擎错误分别记状态；不要静默丢弃异常局。
- [ ] 保存一次完整 replay，并验证选用版本能够播放；对关键状态作一致性核对。

最小交付为：运行命令、配置与版本标识、完整记录、可播放的 replay，以及对一个具体行为或失败的解释。运行产物可在忽略目录保存，文档记录路径/哈希。不要先创建不存在需求的大型实验管理平台。

### 3. 检查直接影响首个实验的风险

- [ ] 覆盖实际用到的观测字段、全局事件、mask 和对象查询的隐藏信息泄漏检查。
- [ ] 测策略决策与 game update 的执行时序；外部推理显式调度，避免未等待的异步回调。
- [ ] 记录实际出生位和随机源控制能力；未完成控制前采用随机分配与分层完整对局比较。
- [ ] 测端到端有效决策吞吐与异常率，不只测空引擎 tick/s。

seed/固定出生位/精确恢复的适配开发，只有在一个具体比较确实需要其精度时才提上日程。没有这些能力仍可以运行正常对局并获得有范围限制的证据。

## 第二轮：从真实失败到首个改进

- [ ] 采用不同倾向的对手收集整局，混合典型事件、失败和随机普通时刻。
- [ ] Agent优先审查新故障、控制器分歧、不确定性及局部/整局冲突，同时保留随机和分层抽查。用户只需反馈体验，Agent关联记录并诊断，不要求用户审实验或查日志。
- [ ] 用 [评估协议](evaluation.md) 分类观察、执行、评估、决策、评测等错误；允许多原因。
- [ ] 选一个高影响且可干预的问题，按 [实验模板](../templates/experiment.md) 列竞争解释。
- [ ] 用简单对照及针对性破坏检查局部测试是否对该能力敏感。
- [ ] 比较最小规则修改、参数优化、规划或学习中的适用替代项；一次只要求有判别力的比较。
- [ ] 保持其他模块和正式评测条件可比；必要时做模块交叉替换。
- [ ] 检查真实局部行为与独立整局结果，报告负面、模糊结果和不确定性。

“没有提升但排除一个原因”可以完成一项研究任务，但不能标记整个 AI 已改善。局部提升而整局退步应继续检查目标与模块交互。没有必要为了达到所谓“首个学习模块”而放弃已经有效的非学习改进。

## 后续按证据触发的分支

| 观察到的瓶颈 | 可开启的方向 | 开始前须具备的条件 |
| --- | --- | --- |
| 有好候选但选择不稳 | 排序监督、局部 RL | 可靠标签/反馈、合法输入、同接口简单基线 |
| 候选集合贫乏 | 扩展计划生成或搜索 | 可执行候选与任务目标 |
| 近似预测误导行动 | 模型校准或真实引擎有限搜索 | 足以检验排序的真实后果，不假设可分叉 |
| 记忆/侦察不足 | 历史表示、探索或意图估计 | 观察协议与信息价值诊断 |
| 某模块交互异常 | A/B 交叉替换 | 各模块可独立替换且预算可比 |
| 对旧对手强、新打法弱 | 多样对手与挑战者 | 固定锚点和独立挑战记录 |
| 初始化噪声妨碍关键比较 | seed/出生位/前缀适配 | 明确需要的控制精度和验证方法 |

首轮无需承诺学习算法、模型大小、GPU 数量或训练小时数。实际资源投入由采样吞吐、基线强度、初步学习曲线与目标增益决定。
