# Supalosa 设计对照：先把基础行为做完整

研究对象是当前固定依赖 `@supalosa/chronodivide-bot@0.6.8-beta.3-165b77a`，对应提交 `165b77a71d0cf5ebd27c65b19d0486bcbae78d0f`。阅读安装包原始 TypeScript、发布 JS 和固定 GitHub 源码，再做一场只增加诊断记录的真实对局及一个独立修理候选。没有改外部锚点或维护中的 0.1.14。

## 先纠正复杂度判断

Supalosa 包含任务调度、进攻/防守/侦察/扩张/工程师任务、战斗小队、地图分区和生产队列；不是只有一个极简状态机。其 `src/bot` 43 个 TS 文件约 4,971 个非空行；我们 0.1.14 Bot 包引用的 28 个自有源文件约 5,186 个非空行（包含打包的历史模式）。口径排除依赖、测试、玩家入口和分析工具，只是体量比较，不是语义复杂度指标，也不支持“多很多倍”的说法。

真正的问题是行为闭环的完成度：我们有多处进退判断和恢复锁定，却漏掉修理、可见中立经济目标等基础动作，攻守之间也存在不同的接战规则。

## 直接值得借鉴的机制

| Supalosa 的实际机制 | 对应我们的具体缺口 | 采用时的边界 |
| --- | --- | --- |
| 进攻任务进入 Attacking 后锁定已分配兵力；战斗期间主要由小队执行，不按全局兵力评分逐次撤销 | `Operations.target`、战略恢复、战术避险各有判断，短暂变化能触发跨地图深撤 | 保持任务承诺，同时保留有证据的救援、局部退让和失败条件；不要照抄几乎不主动撤退 |
| AttackMission 与 DefenceMission 共用 CombatSquad，以及接近、攻击、GI 部署原语 | PositionTactics 与 StrikeTactics 的目标范围和动作规则不同，一侧修好不能保证另一侧 | 合并共同的接战能力，让任务决定地点、范围和退出条件 |
| 小队优先处理附近可攻击的目标；正常行军与返回使用原生 AttackMove；相同指令尽量保持 | 我们有不少 Move/Stop，以及为了追求队形、集火或恢复而持续覆盖行为的路径 | 保留有效碾压和必要避险；不要把 Move 全局替换成 AttackMove，按任务语义验证 |
| 任务提出单位需求，生产按优先级满足；准备人数有下限和等待后的调整 | 生产目标与当前缺少的侦察、守备或作战队伍联系弱，部分等待依赖固定库存条件 | 先接通具体任务缺口，避免一次搬入整套评分/暂停系统 |
| 修理受损建筑、派工程师占领可见产钱建筑 | 主线没有启用修理，也没有中立经济目标任务 | 修理要核对开关状态和资金代价；捕获目标的所有权、守军仍依靠合法观察 |

## 不应误学的内容

- `MatchAwareness.shouldAttack()` 虽有复杂的全局威胁和攻守切换计算，这一固定版没有调用它的决策路径；诊断实局读取次数也是零。不能据此声称其进攻由那套全局门槛驱动。
- 地图分区主要服务可见性、威胁、建造与扩张；战斗路径大部分交给引擎。这不是完整的区域占领规划或人类水平地图理解。
- 集结容许距离很宽、进攻很少主动撤退、个别抓兵参数语义不一致，均不宜照搬。动作去重对位置对象使用引用比较，也不意味着所有坐标相同的动作都能去重。
- 它的集结朝向和某些目标读取敌方实际出生位置；资源/建造查询也有超出我们观察边界的路径。这些输入不能带入我们的策略。借鉴方法时用原始静态地图及合法侦察替代。

[战场状态源码](https://github.com/Supalosa/supalosa-chronodivide-bot/blob/165b77a71d0cf5ebd27c65b19d0486bcbae78d0f/packages/chronodivide-bot/src/bot/logic/awareness.ts) 与已有 [信息边界记录](opponents-and-data.md#24-现成对手有需要披露的信息优势) 支持上述区分。未对原版 RA2 简单电脑做同条件测试，不把玩家难度感受当作严格等价评级。

## 运行核对

`runs/supalosa-design-study`：城市图、固定 0.1.14 主线对原样 Supalosa，14:52 正常结束，主线获胜。仅对 native 方记录任务、原样透传的动作调用及 `shouldAttack` 读取；原始钩子和哈希在 `work/supalosa-study/source-audit.json`，格式整理后的复现钩子为 [supalosa-design-hooks.mjs](../analysis/supalosa-design-hooks.mjs)。

这局观察到最多三个同时攻击中的任务，合计最多 21 个进攻单位；91 次 AttackMove、57 次 Attack、33 次部署调用，以及 20 次修理开启请求。1:40 的采样已经有一座己方油井。该局 Supalosa 自己输了，这些数值只证明机制在运行，不是机制胜率归因。原回放 90 份快照与终局匹配。

固定规则实读：工程师成本 500；油井成功占领的启动收入 1000，之后还有持续收入（规则金额参数为 50）。前提仍是工程师能安全完成占领；没有据此声称新增捕获策略已实现。

对原 16:00 Supalosa 败局，从 native 视角检查 4:00–6:00，六名 GI 共出现 122 次 Para 冷却重启信号。原记录的 97 份快照及终局匹配；这是部署武器实际使用证据，不是命中数或火力效率评分。报告保存在 `work/supalosa-study/loss-native-view`，没有覆盖原来的主线报告。

## 独立修理试验

研究分支 `codex/supalosa-repair-study`，行为候选 `a1d45e5` / `0.1.14-repair.1`；后续 `44d804f` 只补充修理开关的效果记录。新增的观察仅为己方可修理属性和修理开关，按状态开启，避免重复切换。其他战略、生产数量、战术和评分保持。

[对照计划](../experiments/supalosa-repair-study.json)：城市/短图，对 0.1.14 压制、0.1.8 旧阵地、固定 Supalosa，各格每版一局，共十二局。原版与修理版均 **3/6 胜**，全部正常。观察到修理开关和建筑 HP 回升，例如短图旧阵地局碉堡净回升采样合计 366、矿场 147，但仍输了；短图 Supalosa 局电厂净回升采样合计 457。采样净增不是全部修复量，也不等于避免的伤害或净经济收益。

修理已补成可运行候选，未证明综合胜率提升，因此未替换默认。候选 113 项测试与类型检查通过；选定一胜一负原回放另核对 406 份快照及终局。兼容性证据与胜负结论分开。

## 调整下一轮顺序

1. 先统一攻守的接近、有效开火、部署和原生命令保持，解决实际参战问题；任务层表达进攻/保护/局部退让的差异。
2. 清理重复否决和深撤锁定，建立有明确完成、改派、失败条件的持续任务；用上一轮 18:07 反例检验短暂敌情误差不会变成两分钟返家。
3. 地图模块先提供这些任务需要的通路、矿区和侦察观察点；侦察验收覆盖敌家屯兵区，加入可见中立经济目标。不要为了补基础能力先扩大通用规划框架。
4. 将修理、捕获和补兵需求接入可解释的经济优先级，分别看实际收益与资金竞争。继续让主线和压制路线交替适应，固定 Supalosa 作外部参照。

这调整了 [地图与区域控制方案](map-control.md) 的实施顺序；共享战场模型仍需要，但应由这些具体行为驱动。调查与未晋升候选均保留，维护入口继续为 0.1.14。
