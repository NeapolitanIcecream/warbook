# 分析改进：问题、验收与保留决定

2026-09-16。用户要求每项改进解决已观察的问题，结构和性能按研发的同一约定管理。本轮只保留下面三项有实际验收的改进；默认玩家 0.1.4 和冻结 counter 均未替换。

## 1. 批次报告解决重复查询与比较口径遗漏

工具：[compare_runs.py](../analysis/compare_runs.py)。从启动台账读取每局 manifest、initial、result，以每方冻结包身份统计，不用模式名字代替版本。

- 旧 `fixed-pool-counter` 的 48 次启动复算仍为 M0 15/24、counter 17/24；直接交手单列为 counter 9:7，镜像另列。
- 按地图、对手、实际出生位置与创建槽位展示覆盖。槽位平衡不会被解释为出生位置已经平衡，也不会自动重加权或改变旧评分。
- 总次数够而部分条件漏跑、同标签中途换版本、重复记录、结果文件缺失、终局标记与引擎状态矛盾、规则混用，都停止比较并给出错误；有停止类别时逐项保留。
- 方法测试使用小型合成文件，检查上述故障能否被发现；不把这些测试计作游戏证据。旧真实批次和新 16 场试跑都能完整复算。

### 小样本区间的实际修正

新试跑出现了 4/4 与 0/4。未经连续性修正的 Wilson 区间在这两个极小样本中会把 50% 排除在外，容易被误用为强结论。本工具因此采用现有 SciPy 的 Clopper–Pearson 精确二项区间：4/4 的条件 95% 下界约 39.8%，0/4 的上界约 60.2%。[SciPy 官方接口说明](https://docs.scipy.org/doc/scipy/reference/generated/scipy.stats._result_classes.BinomTestResult.proportion_ci.html)

区间仍依赖独立二项抽样假设；没有修复选择偏差、来源相关性或地图泛化问题，也不是对手池增益区间。报告不自动晋升策略。旧胜负定义、分母与固定池分数没有修改。

依赖复用本机已有 SciPy 1.13.1，记录在 [analysis/requirements.txt](../analysis/requirements.txt)；游戏代码不依赖 SciPy。报告记录分析脚本哈希和统计库版本。

## 2. 密集回放解决时间顺序盲点

工具：[encounter.ts](../scripts/encounter.ts)。对原始 replay 做只读重建，每 3 tick 读取装甲位置、HP、速度、攻击状态和武器冷却；通过公开回放事件取得销毁对象与准确 tick。没有调用策略、没有生成另一种动作的反事实后果，也没有增加实时 Bot 日志。

每次重建必须通过：原回放 SHA-256、原日志中所有已记录的单位名称/位置/HP 快照、实际终局 tick、逐方败北与资金核对。不匹配时只留下诊断，不输出可接受的时间线。最终核查 8 个回放、1360 份单位快照全部匹配；故意改错旧日志一处 HP 时，工具定位到唯一不匹配项并拒绝生成有效时间线。分析脚本及信号规则的哈希随报告保存。

仅保留关键事件前 150、后 300 tick 的窗口，完整 replay 始终保留，之后可针对新问题重建其他时段。报告显式区分：

- 观察到的范围内数量、真正的攻击状态与冷却重启信号；距离不自动等于实际参战。
- 精确销毁事件，以及只有 3 tick 区间精度、原因未归属的 HP 变化。
- 某方首条已标记任务指令与首车本身的指令；任务可能首先分配给步兵。
- 原 actor 可见接触与离线查看的对手私有状态。后者只用于诊断，不能输入 actor。

### 真实旧案例带来的新判断

| 旧局 | 新的可核对事实 | 改变了什么判断 |
| --- | --- | --- |
| `regroup-screen/mp06t2.map/0-m1` | 撤退指令在 5886；首车 HP 首次下降位于 6174–6177；销毁事件为 6323。前三辆车有冷却重启记录，第四辆在后方没有同期记录 | 不能简单归因为未及时发出撤退命令；下一步应区分撤退执行、队形与实际可用火力 |
| `regroup-screen/mp03t4.map/1-m1` | 撤退 6060；首次 HP 下降 6072–6075；销毁 6144 | 两种相似失败的时间条件不同，不能共用一个未经区分的原因标签 |
| `raid-initial/mp06t2.map/000-combined` | 获胜，但 `raid-economy` 没有已记录的新指令 | 自动重现“赢了但该任务未被日志证明激活”的反例 |

## 3. 两因素对照解决 counter 的成分混淆

可复现计划：[counter-components.json](../experiments/counter-components.json)。执行器 [matrix.ts](../scripts/matrix.ts) 先从指定 commit 构建各方不可变包，再按计划交错运行并轮换创建槽位，保留全部台账。

- A：开局阶段把无局部接战任务的部队目标设为基地集结点，直到有 4 辆坦克或 tick 9000。
- B：同阶段过滤基地 12 格以外的**显式对象攻击候选**。它并不会关闭引擎的 AttackMove 行为。
- 不改经济/生产、碾压基础、引擎、规则和信息协议。144 份旧观察历史回灌检查中，新拆分的原模式与冻结 M0/counter 的动作输出一致；这只覆盖所测输入历史，不声称精确复刻不同新局。

两张已有开发图、旧 M0 为固定对手、每条件 4 次启动的 16 场试跑均正常结束：

| A | B | 模式 | 正常胜/启动 |
| --- | --- | --- | ---: |
| 关 | 关 | 冻结 M0 | 1/4 |
| 开 | 关 | assembly-only | 4/4 |
| 关 | 开 | contact-filter | 0/4 |
| 开 | 开 | 冻结 counter | 3/4 |

这些是归因试跑，不是独立实力确认。不能把 4/4 作为晋升理由，也不能从 0/4 否定整个方向。

密集回放在短图首轮分别记录到首车首次被观测离开基地 12 格区域时，四种条件的坦克数量为 **1、3、1、4**。这不是进攻承诺或因果收益指标，但结合指令验证了程序开关的不同作用：过滤目标本身仍会继续向外移动；集结目标也可被近处接战打断，且同样作用于早期步兵。后续应优先检验集结目标与允许局部接战的取舍，而不能继续笼统地把 counter 当成一个“等四辆”的单独变量。

## 4. 结构、成本与停止扩建

批次读取、汇总和渲染分开，方便对错误输入做测试。首车与全体装甲使用同一份 [combat-signals.ts](../src/analysis/combat-signals.ts) 规则，避免两套冷却/伤害推断漂移；测试覆盖换武器、采样缺口、不同单位、回血等反例。这是为可靠分析做的范围内重构。

最终核查中，密集重建单局内部计时约 0.85–1.65 秒，关键窗口约 196–459 KiB；旧 48 场批次报告的完整命令墙钟约 0.57 秒，新 16 场报告约 0.40 秒。基础旧局重放约 1.19 秒，内容不同，只报告额外分析成本，不把这些数字称作等价性能提升。当前成本未妨碍下一轮判别实验，维持按需重建和串行运行。

## 5. 使用与下一步

```sh

npm run analyze -- runs/fixed-pool-counter
npm run analyze:encounter -- runs/regroup-screen/mp06t2.map/0-m1
npm run analyze:encounter -- runs/raid-initial/mp06t2.map/000-combined --actor WarbookBlue --task raid-economy
# out 必须是新的实验目录；不能覆盖已有证据。

npm run test:analysis
```

下一轮从这些新判断安排小规模干预；如果新的日志字段、图表或统计方法不能区分当前解释，就不加入流程。分析规则改变需保留版本、说明影响并重算相关报告；评分、目标池或行为协议改变则按既有约定重新比较双方。当前没有新主线晋升，也没有最终留出验证。
